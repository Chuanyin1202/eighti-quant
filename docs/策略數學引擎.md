# 策略數學引擎

**文件目標：** 定義策略 `Step()` 函數的完整輸入輸出契約，以及內部各層（市場狀態感知 / 宏觀引擎 / 微觀引擎 / 底倉釋放）的計算邏輯。本文件是 `internal/strategies/lunar-spot-v1/` 所有程式碼的**唯一**規格依據。

**主線設定：** `lunar-spot-v1` 策略，運行於 Binance 現貨 BTCUSDT / ETHUSDT 雙標的，聚合週期 4h。

---

## 0. 引擎身份

### 0.1 純函數無狀態轉換器

`Step()` 是一個純函數：

```
Step(input StrategyInput, params Params) → output StrategyOutput
```

- 相同 `input + params` **必定**產出相同 `output`（無隨機、無時鐘、無外部依賴）
- 函數內**禁止**：
  - 時鐘類：`time.Now` / `time.NewTimer` / `time.NewTicker` / `time.Tick` / `time.Since` / `time.Sleep` / `time.After` / `time.AfterFunc`
  - 網路類：`net/http` / `net/rpc` / `google.golang.org/grpc` / `gorilla/websocket` / `nhooyr.io/websocket`
  - DB 類：`database/sql` / `gorm.io/*` / `*Tx` / 任何 ORM
  - 檔案類：`os.Open` / `os.OpenFile` / `os.Create` / `os.ReadFile` / `os.WriteFile` / `io/ioutil.*` / `bufio.NewReader(os.Stdin)`
  - 隨機類：`math/rand`（破壞純函數性，若需隨機由 `input` 帶入 seed）
- 所有時間戳、K 線、帳戶狀態必須由 `input` 傳入

#### 0.1.1 時間戳契約 + 同構規則（重要）

**`LatestBarTimeMs` 的定義（一處規定，多處引用）：**

```
LatestBarTimeMs := 最新「已完成」4h bar 的「收盤時間戳」(close timestamp)
                = bar.OpenTime + bar.Duration
                = bar.OpenTime + 4h（4h K 線情境）
```

**為什麼用 close 而不是 open：**

策略決策的「有效時間」是 bar 結束的瞬間（資料齊備、可決策的時點），而不是 bar 開始的瞬間。
- 例：4h bar `2026-04-30 20:00 ~ 2026-05-01 00:00 UTC`
  - bar 開盤時間：`2026-04-30 20:00`（4 月）
  - bar 收盤時間：`2026-05-01 00:00`（**5 月**，月度判定應落入此時點）
- 若用開盤時間做月度判定，5/1 第一個 4h bar 完成時的決策仍會被算為 4 月的第 30 天，**月度預算不會在跨月 0:00 重置**，造成回測與實盤對「幾月」看法不同

**統一用「close timestamp」後**：
- 月底/月初邊界、日邊界、跨月重置全部對齊曆法直覺
- 「決策時間 == bar close time」這個語義在 backtest 跟 live 完全一致

**策略內部時間判定的鐵律：**

策略內部任何「現在是幾號 / 幾點 / 是否新月」的判定**必須統一使用 `input.LatestBarTimeMs`**，禁用 `input.NowMs`。

`NowMs` 與 `LatestBarTimeMs` 的差異：
- 回測時 `NowMs == LatestBarTimeMs`（兩者都是 bar close 時間戳）
- 實盤 cron tick 時 `NowMs` 比 `LatestBarTimeMs` 晚 0~60 秒（cron 觸發時間 vs 最新已完成 bar 收盤時間）
- 月底 23:59:59 跨到 00:00:00 的瞬間，`NowMs` 可能落入新月而 cron 還沒觸發新 bar 的處理，這時舊 bar 仍在舊月 —— 兩者結論不同 → **同構鐵律名義成立、語義破壞**

**統一用 `LatestBarTimeMs`** 確保回測與實盤對所有時間判定結論完全一致。

`NowMs` 只允許用於：診斷輸出、外圈超時保護。內核時間判定**禁止**讀取 `NowMs`。

### 0.2 鐵律複述

1. **複利前置**：策略設計必須能說明資金規模如何隨權益正反饋滾動
2. **回測=實盤同構**：禁止 `if isBacktest` 分支
3. **無 I/O**：禁止網路、DB、檔案、計時器
4. **OHLC 剝離**：本策略 `IsSpot=true`，內核只接受 `[]float64 closes` 與 `[]int64 timestamps`，不依賴 `quant.Bar`
5. **600 bar warm-up**：`len(input.Closes) < 600`（≈ 100 天）時 `Step()` 直接返回空輸出，無交易、無 RuntimeState mutation。原因：EMA600（中期趨勢偵測）與 σ 滾動 90 天分位數（≈ 540 bar）都需要至少 600 bar 充分預熱，否則市場狀態判定退化為 fallback，產生 bootstrap 期偽訊號。資料窗不足是運維問題，由外圈 K 線供應端解決，策略內核**不**做 fallback

### 0.3 雙標的同構原則

`Step()` 不知道自己在跑 BTCUSDT 還是 ETHUSDT。標的差異透過：
- `params.SpawnPoint`（出生點，例如月度注資金額、最小訂單）
- `params.Chromosome`（染色體，由 GA 針對該標的的歷史數據獨立進化）

兩者完全傳達。內核程式碼**不**寫 `if symbol == "BTCUSDT"` 之類的分支。

## 1. 資產結構三態（Portfolio State）

### 1.1 三態定義（Canonical Naming）

| 程式結構名 | LotType 字串 | WS / DB 序列化 | UI 顯示 | 語義 | 來源 |
|------------|--------------|---------------|---------|------|------|
| `DeadAsset` | `"DEAD"` | `"DEAD"` | 長期持倉 | 宏觀長期底倉，原則只進不出 | 宏觀引擎吸入 |
| `FloatAsset` | `"FLOAT"` | `"FLOAT"` | 活躍倉位 | 微觀浮動倉，可自由買賣 | 微觀引擎管理 |
| `ColdSealedAsset` | `"COLD_SEALED"` | `"COLD_SEALED"` | 封存資產 | 冷封存底倉，**永不釋放** | 用戶建立 Instance 時指定的封存比例 |

**整個系統強制使用以上命名**，禁止使用以下舊變體（重構前殘留）：
- ❌ `DeadStack` / `FloatStack` / `ColdSealedStack`
- ❌ `DEAD_STACK` / `FLOATING`
- ❌ `DeadBTC` / `DeadETH`（用泛型 `DeadAsset`）

> 註：本文件用 `Asset` 抽象表示「標的資產」（BTC 或 ETH），**內核計算只用泛型語義**，不含「BTC」「ETH」字眼。

### 1.2 通用會計公式

```
TotalAssetQty   = DeadAsset + FloatAsset + ColdSealedAsset
TotalEquity     = USDTBalance + TotalAssetQty × Price
ReserveFloor    = micro_reserve_pct × TotalEquity
SpendableUSDT   = max(0, USDTBalance - ReserveFloor)
CurrentMicroWeight = (FloatAsset × Price) / TotalEquity     // 注意：分子只算 FloatAsset，不含 Dead/ColdSealed
```

- `micro_reserve_pct`：微觀層保留資金比例（出生點參數，不進化），預設 `0.25`
- `ReserveFloor`：保留作為微觀引擎下次加倉的彈藥，宏觀引擎**不能**動用

### 1.3 標的對應關係

| 交易對 | 標的資產 | USDT 報價 |
|--------|---------|-----------|
| BTCUSDT | BTC | USDT |
| ETHUSDT | ETH | USDT |

每個 Instance 只持有一個標的 + USDT 兩種資產，不做跨標的切換。

## 2. 市場狀態感知層

### 2.1 四態分類

`MarketState` 結構體：

```go
type MarketState struct {
    State                  string  // "NORMAL_BULL" | "NORMAL_BEAR" | "QUIET" | "EXTREME"
    TimeDilationMultiplier float64 // 給宏觀引擎，1.0=正常，>1.0=擴展時間窗口加速定投
    BetaMultiplier         float64 // 給微觀 Sigmoid，1.0=正常，>1.0=加速調倉
    IsQuiet                bool    // true 時微觀粉塵訂單歸零
}
```

### 2.2 判斷規則

判斷依賴兩個維度：**趨勢** 與 **波動**。

**趨勢維度**：基於 EMA 排列（4h bar 上窗長拉長到中期）
- `EMA200 > EMA600 × 1.005`（多 0.5% 緩衝避免黏連）→ `Bullish`
- `EMA200 < EMA600 × 0.995` → `Bearish`
- 否則 → `Sideways`

> EMA200 在 4h ≈ 33 天，EMA600 在 4h ≈ 100 天。原始設計用 EMA50/200（≈ 8/33 天）審查發現對 BTC 真實牛熊週期（季度級）偵測過度敏感、fakeout 多。改長之後 EMA crossover 反映的是「中期趨勢翻轉」而非「短期回調」。

**波動維度**：基於最近 30 根 4h K 線的 σ（對數收益率標準差）相對於滾動 90 天的分位數
- σ 占比 > 90% 分位 → `HighVol`（注意：移除「24h 漲跌 > 8%」固定閾值，因 BTC/ETH 分布不同；改純分位數判斷，標的自適應）
- σ 占比 < 30% 分位 → `LowVol`
- 否則 → `MidVol`

> 滾動窗口從 365 天縮到 90 天，因 BTC 真實波動結構切換多在 1-2 週完成，365 天滾動會讓狀態判定滯後 1-2 月。

**四態映射**（重做：溫和牛市不再裝睡）：

| 趨勢 | 波動 | State | TimeDilation | BetaMul | IsQuiet |
|------|------|-------|--------------|---------|---------|
| Bullish | LowVol | `NORMAL_BULL` | 1.0 | 0.8 | false |
| Bullish | MidVol | `NORMAL_BULL` | 1.0 | 1.0 | false |
| Bearish | LowVol | `NORMAL_BEAR` | 1.3 | 0.8 | false |
| Bearish | MidVol | `NORMAL_BEAR` | **1.5** | 1.0 | false |
| Sideways | LowVol | `QUIET` | 1.0 | 0.5 | **true** |
| Sideways | MidVol | `NORMAL_BULL`（保守歸類） | 1.0 | 1.0 | false |
| 任意 | HighVol | `EXTREME` | 1.0 | **2.5** | false |

**關鍵修正：**
- **`Bullish + LowVol = NORMAL_BULL`（不是 QUIET）**：溫和牛市是 BTC 最常見形態（2023 全年、2024 上半年），這時策略必須繼續加倉才能享受複利。原設計把它判為 QUIET 會在最該漲的時候裝睡，**直接違反鐵律 1 複利前置**。
- **只有 `Sideways + LowVol` 才是 QUIET**：真正的盤整（無趨勢 + 低波動）才應該降頻減交易成本。
- **`Bearish + LowVol`（陰跌）`TimeDilation=1.3`**：低波熊市也應該繼續定投，但因為波動小不需太激進。

### 2.3 設計理由

- **熊市加速定投**（`TimeDilation=1.5` MidVol / `1.3` LowVol）：跌的時候撿便宜是 DCA 的精髓
- **極端時加速調倉**（`BetaMul=2.5`）：暴漲暴跌時 Sigmoid 響應加快，避免錯失關鍵點位
- **真盤整才降頻**（`BetaMul=0.5 + IsQuiet=true`，僅 Sideways+LowVol）：減少手續費損耗
- **EMA 窗長拉長**：EMA200/600 反映中期趨勢，避免短期 fakeout 誤判
- **σ 滾動窗縮短 + 移除絕對閾值**：90 天滾動分位數對標的自適應，不需手調 BTC vs ETH 的絕對閾值
- **不上 HMM/馬可夫**：規則式四態算力低、可解釋、能跑通；機率模型留作 Phase 14+ 升級

### 2.4 邊界情況

- 數據不足（K 線少於 600 根 4h bar，約 100 天）→ 強制返回 `QUIET` 並印警告
- σ 計算結果為 0（極稀有，例如停盤）→ 視為 `QUIET`
- σ 滾動分位數的歷史窗（90 天）不足時 → 用實際可用窗計算，不退化到 fallback

## 3. 信號與目標函數框架

策略採用「**意圖層 + 過濾層**」二段結構：

```
意圖層：
  - Macro Engine  → MacroIntent  (BUY only, 進入 DeadAsset)
  - Micro Engine  → MicroIntent  (BUY/SELL, 操作 FloatAsset)
  - Release Logic → ReleaseIntent (DeadAsset → FloatAsset 帳本轉換)

過濾層（內建在各引擎內部）：
  - 楔形區過濾（防粉塵）
  - 最小訂單閾值（10.1 USDT）
  - SpendableUSDT clamp
  - 全局止損熔斷
```

## 4. 宏觀引擎（Macro Engine）

### 4.1 設計理念

宏觀引擎負責**長期累積底倉**，本質是「**動態加速版的月度 DCA**」：
- 每月固定預算
- 平日按日均勻分配
- 行情極端時加速消化預算
- 月底死線兜底（防資金閒置）
- **只買不賣**（賣出由微觀引擎或人工釋放規則處理）

### 4.2 月度預算機制

每個自然月的 1 號 0:00 UTC，宏觀引擎分配當月預算（per-tick 累積機制詳見 §4.3）：

```
MonthlyBudget = MonthlyInjectUSDT  (出生點參數，不進化)
```

**狀態追蹤**（持久化於 `RuntimeState`）：

```go
type MacroRuntimeState struct {
    CurrentMonthYearMonth string  // "2026-05"
    MonthlyBudget         float64
    SpentThisMonth        float64
    PendingMacroBudget    float64 // per-tick 累積但尚未下單的預算（USDT）
                                  // 跨月 carry over，達到 MinOrderUSDT 才下單
    LastMacroBuyBarTime   int64
}
```

### 4.3 每 tick 決策邏輯（per-tick 累積 + 10.1 USDT 訂單門檻）

**所有時間判定一律使用 `input.LatestBarTimeMs`（不是 `NowMs`）**，理由見 §0.1.1。

**核心機制（兩條）：**
1. **carry balance** — per-tick 累積到 ≥ MinOrderUSDT 才下單
2. **Idempotent guard 必須前置** — `LastMacroBuyBarTime == LatestBarTimeMs` 的檢查放在所有 state mutation 之前，等價於「此 bar 已處理 → 整個函數 zero-mutation early return」。後置檢查 + rollback 在 deadline 路徑下無法完整復原（因為 deadline 已 zero PendingMacroBudget 並 += SpentThisMonth），retry 會丟失預算。

per-tick 預算（如 monthly 600 / (31×6) ≈ 3.23 USDT）通常 << 最小訂單 10.1 USDT。若每 tick 都觸發過濾，整月不下單、最後死線一次性買 600 USDT，**完全違反 DCA 節奏**。

正確做法：**累積到能下單再下單**。

```
RuntimeState.Macro 新增欄位：
  PendingMacroBudget float64  // 已累積但尚未下單的 macro 預算（單位 USDT）

時間衍生量（從 LatestBarTimeMs 計算，UTC 時區）：
  YearMonth        = format(LatestBarTimeMs, "YYYY-MM")
  DayOfMonth       = day(LatestBarTimeMs)             // 1..31
  DaysInMonth      = days_in_month(LatestBarTimeMs)   // 28..31
  BarsPerDay       = 24h / 4h = 6                     // 4h tick 模型
  BarOfDay         = floor(hour(LatestBarTimeMs) / 4) // 0..5

# ──────────────────────────────────────────────────
# Step 0: 同 bar idempotent guard（**必須前置**，所有 mutation 之前）
# ──────────────────────────────────────────────────
1. 若 LastMacroBuyBarTime == LatestBarTimeMs:
     return MacroIntent{ OrderUSD: 0 }, Runtime.Macro  // 零 mutation early return

# ──────────────────────────────────────────────────
# Step 1: 跨月處理（首次進入新月才執行）
# ──────────────────────────────────────────────────
2. 跨月檢查：YearMonth != Runtime.Macro.CurrentMonthYearMonth
     → 重置 MonthlyBudget = MonthlyInjectUSDT
     → 重置 SpentThisMonth = 0
     → **保留** PendingMacroBudget（carry over 跨月，避免月初零頭被丟棄）
     → 更新 CurrentMonthYearMonth = YearMonth

# ──────────────────────────────────────────────────
# Step 2: 計算累積額度
# ──────────────────────────────────────────────────
3. 計算當月剩餘 bar 數：
     RemainingDays      = DaysInMonth - (DayOfMonth - 1)
     RemainingBarsToday = BarsPerDay - BarOfDay        // 含當前這個 bar
     RemainingBars      = (RemainingDays - 1) × BarsPerDay + RemainingBarsToday
     RemainingBudget    = MonthlyBudget - SpentThisMonth - PendingMacroBudget

4. 每 tick 基準累積額度：
     PerTickBase = RemainingBudget / max(RemainingBars, 1)
     PerTickAccelerated = PerTickBase × MarketState.TimeDilationMultiplier
                                     × MacroAccelerator(若 EXTREME)
     PendingMacroBudget += PerTickAccelerated

# ──────────────────────────────────────────────────
# Step 3: 決定本 tick 是否下單
# ──────────────────────────────────────────────────
5. 決定本 tick 是否下單：
     IsDeadline = (DayOfMonth >= MacroDeadlineDays)
     CanFire    = (PendingMacroBudget >= MinOrderUSDT) OR IsDeadline

     if !CanFire:
         OrderUSD = 0
         // 下次 tick 繼續累積；不重置 PendingMacroBudget

     else if IsDeadline:
         // 死線：花光剩餘月度預算
         AvailableThisMonth = MonthlyBudget - SpentThisMonth
         OrderUSD = min(AvailableThisMonth, SpendableUSDT)
         PendingMacroBudget = 0  // 死線清零
         SpentThisMonth += OrderUSD

     else:
         // 正常下單：把累積的 carry balance 轉為訂單
         OrderUSD = min(PendingMacroBudget, RemainingBudget+PendingMacroBudget, SpendableUSDT)
         if OrderUSD < MinOrderUSDT:
             OrderUSD = 0    // SpendableUSDT 不夠 → 跳過
         else:
             PendingMacroBudget -= OrderUSD
             SpentThisMonth += OrderUSD

# ──────────────────────────────────────────────────
# Step 4: 標記 bar 處理完成（所有 mutation 之後）
# ──────────────────────────────────────────────────
6. 更新 RuntimeState.Macro.LastMacroBuyBarTime = LatestBarTimeMs
   產出 MacroIntent { Action: BUY, Engine: MACRO, LotType: "DEAD", AmountUSDT: OrderUSD }
```

**Worked Examples（必須 unit test 對得上）：**

假設 `MonthlyInjectUSDT = 600`、`MinOrderUSDT = 10.1`、`MacroAccelerator = 1.0`、`MarketState.TimeDilation = 1.0`、`MacroDeadlineDays = 28`：

| Tick | DayOfMonth | BarOfDay | PendingMacroBudget(prev) | PerTickAccelerated | PendingMacroBudget(new) | OrderUSD | 行為 |
|------|-----------|----------|-------------------------|--------------------|------------------------|----------|------|
| 1 | 1 | 0 | 0 | 3.23 | 3.23 | 0 | 累積 |
| 2 | 1 | 1 | 3.23 | 3.23 | 6.45 | 0 | 累積 |
| 3 | 1 | 2 | 6.45 | 3.23 | 9.68 | 0 | 累積 |
| 4 | 1 | 3 | 9.68 | 3.23 | 12.91 | 12.91 | **下單**，餘 0 |
| 5 | 1 | 4 | 0 | 3.23 | 3.23 | 0 | 累積 |
| ... | | | | | | | 約每 4 tick (16h) 下一筆 |
| 168 | 28 | 0 | 5.5 | ~3.23 | 8.7 | 8.7 + 剩餘 | **死線觸發**，全花光 |

**Carry balance 的好處：**
- 每約 4 個 4h tick（16 小時）下一筆 ~12 USDT，貼近真實 DCA 節奏
- baseline 對比也用同機制（§3.2），fitness 公平
- `Bear + TimeDilation=1.5` 時累積更快，自然加速；同時保證每筆訂單都過 10.1 門檻
- 跨月 carry over：避免月初零頭被忘記；下個月的累積跟上月零頭合算

> 鐵律：本演算法**禁止**讀 `input.NowMs`。回測與實盤對「現在幾號」必須有完全一致的判定。

### 4.4 鐵律

- **只產出 BUY 意圖**，絕不產出 SELL
- 訂單金額必與 `SpendableUSDT` 做 clamp（不能超過可用資金）
- 小於 10.1 USDT 的訂單不執行（粉塵拦截）
- 同一 4h bar 內最多下一次（避免重複）

### 4.5 複利如何發生

宏觀引擎用「絕對 USDT 額度」（`MonthlyInjectUSDT`），**不**做相對權益的滾動。但用戶可選擇將「外部新注資」設為 `MonthlyInjectUSDT × (1 + growthRate)`，由 SaaS 訂閱層處理（不在策略內部複利）。

策略內的複利完全由**微觀引擎**承擔：`TheoreticalUSD = DeltaWeight × TotalEquity`，TotalEquity 隨權益增長 → 訂單規模隨之放大 → 自然複利。

## 5. 微觀引擎（Sigmoid 動態天平）

### 5.1 核心公式

```
EffectiveBeta  = max(0.01, Beta × MarketState.BetaMultiplier)
InventoryBias  = clamp(CurrentMicroWeight, 0, 1) - 0.5
Exponent       = EffectiveBeta × Signal + Gamma × InventoryBias
TargetWeight   = 1 / (1 + exp(Exponent)),  clamp(0, 1)
DeltaWeight    = TargetWeight - CurrentMicroWeight
TheoreticalUSD = DeltaWeight × TotalEquity
```

**符號約定（重要）：**
- `Signal > 0` = 看空訊號（預期降低倉位）
- `Signal < 0` = 看多訊號（預期提高倉位）
- 因 Sigmoid 含 `1/(1+exp(Exponent))`，Exponent 越大 → TargetWeight 越小

`TheoreticalUSD > 0` 時為 BUY 訂單金額（USDT），`< 0` 時為 SELL（abs 值對應賣出資產的 USDT 等價）。

#### 5.1.1 Sigmoid 符號 Sanity Check（必驗）

實作 `micro_engine.go` 後必須跑以下三組測試確認方向正確：

| 場景 | 輸入 | 預期 Exponent | 預期 TargetWeight | 預期方向 |
|------|------|---------------|-------------------|---------|
| **看空中性倉** | Signal=+1.0, β=1.5, γ=0.5, CurrentWeight=0.5 | InvBias=0, Exp=+1.5 | 1/(1+e^1.5) ≈ 0.18 | DeltaWeight ≈ -0.32（賣） |
| **看多中性倉** | Signal=-1.0, β=1.5, γ=0.5, CurrentWeight=0.5 | InvBias=0, Exp=-1.5 | 1/(1+e^-1.5) ≈ 0.82 | DeltaWeight ≈ +0.32（買） |
| **無信號高倉位** | Signal=0, β=1.5, γ=0.5, CurrentWeight=0.8 | InvBias=+0.3, Exp=+0.15 | ≈ 0.46 | DeltaWeight ≈ -0.34（弹簧拉回中性） |

任一行驗證失敗 → 公式或因子定義有負號錯誤。**這個 sanity check 必須在 Phase 4 第一次提交策略代碼時直接通過，否則整個策略反向跑**。

### 5.2 Signal 三因子合成（重定義去共線）

審查發現原設計三因子 `X1 / X2 / X3` 高度共線（VIF 估計 > 5），實際自由度只有 1.5 個。重新定義使三者語義獨立：

```
X1_Reversion = (Close - EMA21) / max(σ21, SigmaFloor)
                // 短期均值回歸：價格高於均線 → X1 > 0 → 看空（預期回落）
                // 注意：移除原版的負號（原版錯把「看多」與「Signal>0」對齊）

X2_Trend     = (EMA21 - EMA60) / max(σ60, SigmaFloor)
                // 中期趨勢：短均線高於中均線 → X2 > 0 → 但同樣對應「看空」？
                // 設計選擇：把 X2 的符號定義為「正值 = 看空」與整體訊號約定一致
                // 解讀：短期過熱於中期 → 預期回落 → 看空
                // GA 可透過 SignalW_Trend 翻號（[-2, 2] 邊界允許負權重，
                // 若 GA 學到「順勢交易比反趨勢好」會自動把 W_Trend 設為負值）

X3_Breakout  = max(0, (Close - Max(Closes[-21:-1])) / max(σ21, SigmaFloor))
                // 上方突破：近 21 根（不含當根）最高收盤之上才有訊號
                // 用 max(0, ...) 變單邊訊號（只有突破時非零，否則 0）
                // 突破常規視為看多（順勢買入）→ X3 > 0 對應「看多」
                // 與整體「Signal>0=看空」約定相反 → SignalW_Breakout
                //   理論上應為負才順勢，GA 自然會學

Signal = SignalW_Reversion × X1_Reversion
       + SignalW_Trend     × X2_Trend
       + SignalW_Breakout  × X3_Breakout
```

**關鍵修正：**
1. **X1 移除錯誤的負號** — 原版 `-(Price-EMA21)/σ21` 把「價格低於均線」對應到 X1>0（即看多訊號），但約定 `Signal>0=看空` 衝突。修為 `(Close-EMA21)/σ` 後，X1 直接表示偏離 z-score，符號與「看空」對齊。
2. **X2 從 `log(Price/EMA21)×5` 改為 `(EMA21-EMA60)/σ60`** — 原版與 X1 在小偏離時泰勒展開等價（共線）。新版用兩條 EMA 的差，反映中期趨勢，與短期 X1 真正獨立。
3. **X3 從雙邊改為單邊（max(0, ...)）** — 只在「上方突破」時非零，避免「下跌穿支撐」與 X1 的負偏離高度相關。

**與 GA 的互動：**
- 染色體 `SignalW_*` 邊界 `[-2, 2]`，允許 GA 學到「順勢」（W_Trend < 0）或「反趨勢」（W_Trend > 0）
- 文件**不替策略預設方向**，由 GA 在 BTC/ETH 各自的歷史中找最優符號

固定常量（不進化）：
- `MicroSignalEMAShortBars = 21`（X1, X3 的短窗）
- `MicroSignalEMALongBars = 60`（X2 的中期窗）
- `MicroSignalStdDevBars = 21`（X1, X3 的 σ 計算窗）
- `MicroSignalStdDevLongBars = 60`（X2 的 σ 計算窗）

#### 5.2.1 三因子相關性 Sanity Check（M2-zero 必驗）

進 Phase 2 之前必須跑以下檢查：
1. 拉 BTC/ETH 各自 5 年 4h K 線
2. 計算 `X1, X2, X3` 三個序列
3. 算 Pearson 相關矩陣 + VIF（Variance Inflation Factor）
4. **驗收標準：** 任兩因子相關係數 |r| < 0.6，VIF < 5

任一指標未過 → 進一步調整 X 因子定義或砍到 2 因子。**不過此檢查不得進入 Phase 4 寫 Step()**。

### 5.3 楔形過濾（Wedge Filter）

```
VolatilityRatio = clip(MAVAbsChange(closes, MicroVolRatioShortBars=16) /
                       MAVAbsChange(closes, MicroVolRatioLongBars=112), 0.1, 3.0)
                  // 數據不足時回傳 1.0

過濾規則：
  if abs(TheoreticalUSD) >= 10.1:
      OrderUSD = TheoreticalUSD                 // 直接下單
  elif 0 < abs(TheoreticalUSD) < 10.1:
      if !MarketState.IsQuiet AND
         (abs(DeltaWeight) >= WedgeDeltaThr OR VolatilityRatio >= WedgeVolRatioThr):
          OrderUSD = sign(TheoreticalUSD) × 10.1   // 強制最小訂單
      else:
          OrderUSD = 0
  else:
      OrderUSD = 0
```

### 5.4 設計哲學（弹簧系統解讀）

```
Signal           = 外力（市場信號）
InventoryBias    = 弹簧恢復力（離 0.5 中性點越遠拉力越大）
Beta             = 弹簧剛度
Gamma            = 是否啟用弹簧（0=純信號驅動，>0=疊加均值回歸）
VolatilityRatio  = 楔形過濾，控制安靜期粉塵
```

### 5.5 微觀層硬釋放

當微觀引擎產出 `OrderUSD < 0` 但 `FloatAsset × Price < |OrderUSD|` 時：
1. 從 `Lots` 篩出 `Type == "DEAD" AND IsColdSealed == false`（不限老化時間）
2. 按 `BuyTimeMs` 升序（FIFO）累積至補足缺口
3. 產出 `ReleaseIntent { Kind: "hard_release", Slices: [...], TotalQtyAsset: ... }`（用 partial lot 結構，同 §6.1）
4. 在同一 `StrategyOutput.Releases` 中，這個硬釋放必須排在 `Intents` 中對應 SELL 的「邏輯前面」（外圈先釋放再賣出）

寫 `AuditLog { event_type: "hard_release", ... }`

## 6. DeadAsset 釋放規則

### 6.1 軟釋放（Soft Release）

每次 `Step()` 都會檢查 `in.Portfolio.Lots`：

```
1. 從 Lots 篩出合格 lot:
   - Type == "DEAD"
   - IsColdSealed == false
   - (LatestBarTimeMs - BuyTimeMs) >= DeadAgingMonths × 30 × 86400 × 1000
   按 BuyTimeMs 升序排序（FIFO）

2. 計算「微觀彈藥缺口」:
   TargetMicroWeight = TargetMicroWeightFloor   // 染色體欄位，預設 0.15
   CurrentMicroWeight = (FloatAsset × Price) / TotalEquity
   MicroWeightGap = max(0, TargetMicroWeight - CurrentMicroWeight)

3. 觸發條件: MicroWeightGap > 0 AND 合格 lot 非空

4. 計算釋放數量:
   eligibleQty = sum(lot.Qty for lot in 合格 lots)
   ReleaseQty = min(
       eligibleQty × MaxReleasePct,             // 不超過合格 lot 總量的 MaxReleasePct
       MicroWeightGap × TotalEquity / Price     // 不超過微觀缺口
   )

5. 從合格 lots 中按 FIFO 順序累積，**支援 partial lot**:
   Slices = []   // 每個元素 { LotID, Qty }，可包含 oversized lot 的部分切片
   累計 = 0
   for lot in 合格 lots (FIFO):
       remaining = ReleaseQty - 累計
       if remaining <= 0:
           break
       takeQty = min(lot.Qty, remaining)   // 第一個過大 lot 取部分；後續 lot 取整或剩餘
       Slices.append({ LotID: lot.ID, Qty: takeQty })
       累計 += takeQty

6. 產出 ReleaseIntent {
       Kind: "soft_release",
       Slices: Slices,            // 至少一個 slice；單一 lot 可能 takeQty < lot.Qty（partial）
       TotalQtyAsset: 累計,        // = sum(Slices[i].Qty)，便於外圈快速取總量
   }
```

**Partial lot 規則（重要）：**
- 第一個 FIFO eligible lot 若 Qty > ReleaseQty，僅釋放 ReleaseQty 那部分，**不能 break 跳過**（否則永遠卡死）
- 外圈收到 `ReleaseIntent` 後，對 `Slices[i].Qty < lot.Qty` 的 partial slice：
  - 將原 lot 拆為兩筆：保留 `(lot.Qty - takeQty)` 為 DEAD（保留原 ID 或新建衍生 ID 由實作決定，但 BuyPriceUSDT/BuyTimeMs 必須延續）
  - 釋放出 `takeQty` 為新的 FLOAT lot（保留 BuyPriceUSDT/BuyTimeMs）
  - 寫 audit log 記錄拆分

**關鍵設計：**
- 「CurrentMicroWeight 目標值」明確定義為 `TargetMicroWeightFloor`（不是 Sigmoid 算出的 TargetWeight）
- 釋放只改 lot.Type 為 `"FLOAT"`，**保留 BuyPriceUSDT 與 BuyTimeMs**（成本與年齡跟隨 lot）
- 由 SaaS 外圈接收 ReleaseIntent 後做 DB 帳本轉換，**不**下發 TradeCommand 給 Agent
- 寫 `AuditLog { event_type: "soft_release", lot_ids: [...], qty: ... }`

### 6.2 硬釋放（Hard Release）

見第 5.5 節。

### 6.3 鐵律

- `IsColdSealed=true` 的 lot **任何情況下不可被釋放**
- 釋放只更新 SaaS 帳本（lot type 標籤），**不**向 Agent 下發 TradeCommand
- 每次釋放必寫 `AuditLog`

## 7. 可進化參數契約（Chromosome）

### 7.1 染色體欄位（13 個，全部進化）

| 欄位 | 邊界 [min, max] | 預設值 | 步長 GeneStep | 語義 |
|------|----------------|--------|---------------|------|
| `Beta` | [0.1, 5.0] | 1.5 | 0.1 | Sigmoid 激進係數 |
| `Gamma` | [0.0, 2.0] | 0.5 | 0.05 | 倉位偏置（弹簧剛度） |
| `SigmaFloor` | [0.001, 0.05] | 0.005 | 0.001 | σ 下限，防止除零 |
| `SignalW_Reversion` | [-2.0, 2.0] | **0.5** | 0.1 | 短期均值回歸權重（GA 自學符號方向；預設非零確保 seed 確定性） |
| `SignalW_Trend` | [-2.0, 2.0] | 0.0 | 0.1 | 中期趨勢權重（負值=順勢、正值=反趨勢） |
| `SignalW_Breakout` | [-2.0, 2.0] | 0.0 | 0.1 | 上方突破權重（負值=順勢買入） |
| `WedgeDeltaThr` | [0.01, 0.1] | 0.03 | 0.005 | 楔形權重變動閾值 |
| `WedgeVolRatioThr` | [1.2, 2.5] | 1.5 | 0.05 | 楔形波動率閾值 |
| `MacroAccelerator` | [1.0, 3.0] | 1.5 | 0.1 | EXTREME 行情下宏觀加速倍率 |
| `MacroDeadlineDays` | [25.0, 30.0] | 28.0 | 1.0 | 月底死線觸發日（整數，clamp 後 round） |
| `DeadAgingMonths` | [3.0, 24.0] | 6.0 | 1.0 | 底倉老化釋放門檻（整數） |
| `MaxReleasePct` | [0.05, 0.3] | 0.15 | 0.01 | 單次最大釋放比例 |
| `TargetMicroWeightFloor` | [0.05, 0.3] | 0.15 | 0.01 | 微觀層權重下限（保證帳戶留有彈藥） |

### 7.2 結構約束（Clamp 必修復）

1. **三個 SignalW 至少一個有效**：`abs(W_Reversion) + abs(W_Trend) + abs(W_Breakout) >= 0.1`，否則指派 `W_Reversion = +0.5`（**確定性 fallback**，不用隨機）。注意：此 Clamp 規則對 `DefaultSeedChromosome` 是 no-op（種子已內建非零 W_Reversion）；對 GA `Sample()` 採樣到的全零個體會修正為 W_Reversion=+0.5。**禁止用隨機 fallback** —— 否則 seed 與 fingerprint 在不同部署間不一致
2. **整數欄位先 clamp 再 round**：`MacroDeadlineDays`、`DeadAgingMonths` clamp 到邊界後 `round()` 為整數，並在 chromosome 中以整數型態 store（避免 Fingerprint 因浮點誤差判錯）
3. **楔形閾值能觸發最小訂單**：`WedgeDeltaThr × InitialCapitalUSDT >= MinOrderUSDT`（軟提示，由 GA 自然淘汰違反者）
4. **TargetMicroWeightFloor < 0.5**：強制低於 Sigmoid 中性點，避免微觀層永遠想加倉

> 註：`TargetMicroWeightFloor` 在 §8.3 Step 流程中作用為「TargetWeight 經 Sigmoid 計算後若低於此 Floor，強制取 Floor」。確保微觀層權重不會在強烈看空時長期歸零、保留再買入彈藥。

### 7.3 出生點 SpawnPoint（不進化、Epoch 級凍結）

```go
    InitialCapitalUSDT float64  // 用戶設定，例如 1000 USDT
    ColdSealedPct      float64  // 用戶設定，例如 0.1 = 10% 永久封存
    MicroReservePct    float64  // 預設 0.25

    GlobalStopLossPct float64  // 全局止損，例如 0.5 = 權益跌至 50% 強制停止
    FeeRate           float64  // Binance 現貨 0.001 (0.1%)
```

### 7.4 預設冠軍（DefaultSeedChromosome）

當 DB 無精英基因時，GA 第一個個體使用上表「預設值」欄位的組合作為種子。此種子是「保守的中性配置」，不保證跑得贏 DCA，由 GA 進化找出更優解。

**確定性保證（rev: docs/m2-pre-9）：**

`DefaultSeedChromosome` **必須在所有部署、所有時點、跑出相同的 chromosome bytes 與 Fingerprint**。具體做法：
1. 預設值表中 `SignalW_Reversion = +0.5` 是非零的，Clamp 結構約束 1（「三個 SignalW 至少一個有效」）已自動滿足
2. Clamp fallback 規則本身改為**確定性**（指派 `W_Reversion = +0.5`，不用隨機）
3. seed 構造不走 GA `Sample(rng)` 路徑，直接從 `DefaultSeedChromosome` 常量複製，**不引入 RNG**

任一步驟若引入隨機，bootstrap 階段就會 break：兩個乾淨部署的 fingerprint 不同 → 進化結果無法 cross-validate → 災難。

### 8.3 Step() 主流程（按順序）

```
func Step(in StrategyInput, p Params) StrategyOutput {
    // 1. 數據窗口檢查
    // 全域 warm-up: EMA600 跟 σ 滾動分位數 (90 天 ≈ 540 bar) 都需要至少 600 bar
    // 不足時返回空輸出（無交易、無 mutation）
    if len(in.Closes) < 600 { return EmptyOutput(in.Runtime) }

    // 2. 帳戶會計
    totalEquity := in.Portfolio.USDTBalance + 
                   (in.Portfolio.DeadAsset + in.Portfolio.FloatAsset + in.Portfolio.ColdSealedAsset) * in.Portfolio.Price
    reserveFloor := p.SpawnPoint.Policy.MicroReservePct * totalEquity
    spendableUSDT := math.Max(0, in.Portfolio.USDTBalance - reserveFloor)
    currentMicroWeight := (in.Portfolio.FloatAsset * in.Portfolio.Price) / totalEquity

    // 3. 市場狀態（用 LatestBarTimeMs，禁用 NowMs，見 §0.1.1）
    marketState := quant.ComputeMarketState(in.Closes, in.LatestBarTimeMs)

    // 4. 宏觀引擎（用 LatestBarTimeMs 做月度判定，禁用 NowMs）
    newMacroState, macroIntent := macro.Decide(
        in.Runtime.Macro, in.LatestBarTimeMs, spendableUSDT,
        marketState, p.Chromosome.MacroAccelerator, p.Chromosome.MacroDeadlineDays,
        p.SpawnPoint.Policy.MonthlyInjectUSDT,
    )

    // 5. 微觀引擎
    microIntent, microDiag := micro.Decide(
        in.Closes, in.Portfolio.Price, currentMicroWeight, totalEquity,
        marketState, p.Chromosome,
    )

    // 6. 底倉釋放
    softRelease := release.MaybeSoftRelease(in.Portfolio, currentMicroWeight, p.Chromosome)
    hardRelease := release.MaybeHardRelease(microIntent, in.Portfolio)

    // 7. 全局止損熔斷
    if totalEquity <= p.SpawnPoint.Policy.InitialCapitalUSDT * (1 - p.SpawnPoint.Risk.GlobalStopLossPct) {
        return HaltOutput(in.Runtime)  // 清空意圖，不產出新訂單
    }

    // 8. 組裝輸出
    return StrategyOutput{
        Intents: collectIntents(macroIntent, microIntent),
        Releases: collectReleases(softRelease, hardRelease),
        NewRuntime: RuntimeState{ Macro: newMacroState },
        Diagnostics: mergeDiag(microDiag, marketStateDiag(marketState)),
    }
}
```
