# 00 — EightiQuant 架構總覽

**文件目標：** 定義 EightiQuant 的三端架構、framework 分層、paper / live 雙模式、以及全局狀態流轉。**不含具體策略邏輯**（見 `strategies/`）、**不含 GA 演算法細節**（見 `20-進化計算引擎.md`）、**不含 paper broker 模擬規則**（見 `30-Paper-Trade-模式.md`）。

---

## 0. 設計哲學

### 0.1 定位
EightiQuant 是一個**量化交易框架（framework）**，不是某個特定策略的實作。它提供：
- 三端架構骨架（雲端 / 本地執行端 / 算力端）
- 策略 SDK（Strategy 接口 + 可選 GA 進化）
- 通用 building blocks（signals / regimes / engines）
- Paper / Live 雙模式（demo 不需要真錢）

具體策略以 **reference 實作** 形式存在於 `strategies/` 目錄，可隨時新增、刪除、抽換。

### 0.2 時空正交與無記憶解算
所有業務推進必須封裝為離散的「動作」，動作之間嚴禁隱式狀態傳遞。每個動作讀入當前狀態快照，產出新的確定性意圖，不依賴上一動作的記憶體變數。

### 0.3 窗口原則
每個模組只能讀取屬於自己的「資料窗口」和「資金窗口」。策略模組看不到資料庫狀態，宏觀引擎看不到微觀浮倉細節，進化引擎看不到實盤帳戶。

## 1. Framework 三層分層

```
┌──────────────────────────────────────────────────────────────┐
│  Application 層：strategies/<策略名>/                          │  ← 用戶寫的策略
│  範例：simple-dca, grid, lunar-spot-v1                        │
├──────────────────────────────────────────────────────────────┤
│  Strategy SDK 層：internal/strategy/                          │  ← 給策略用的接口
│  - Step() 純函數契約                                           │
│  - EvolvableStrategy 8 動詞                                   │
│  - StrategyInput / StrategyOutput                             │
│  - Building blocks: signals / regimes / engines               │
├──────────────────────────────────────────────────────────────┤
│  Framework Core 層：internal/saas, internal/agent, internal/quant │  ← 工程基礎
│  - GA 進化引擎（黑盒，策略無關）                                │
│  - WS Hub / Promote / Pending Reconcile / Fill Compensation   │
│  - Broker 接口（Binance / Paper）                              │
│  - GORM Code-First / API Key 隔離                              │
└──────────────────────────────────────────────────────────────┘
```

**Framework 鐵律**：
- Framework Core **不知道**任何具體策略名稱
- Strategy SDK **不依賴**任何具體 broker 實作
- Application 層**完全可抽換**，刪掉一個策略不影響其他

## 2. 三端物理部署形態

| 角色 | 部署 | `app_role` | 職責 | 限制 |
|------|------|------------|------|------|
| **SaaS 雲端** | 雲伺服器 | `saas` | 決策大腦：cron tick / Step() / WS 下發 / 帳本 | 不持 API Key；`live` 模式禁止觸發 GA |
| **LocalAgent** | 用戶本地 | （無 app_role，獨立進程）| 執行手：呼叫 Binance REST 下單 / 上報 DeltaReport | 不含策略代碼；不連 DB；不自主決策 |
| **Lab 算力端** | 本地算力 | `lab` | GA 進化 / 回測運算 | 連同一個 Postgres；禁止下發實單 |

### 2.1 `app_role` 三態行為矩陣

| 角色 | 開放能力 | 限制 |
|------|---------|------|
| `saas` | 實例管理、交易指令下發、用戶營運 | 禁止 GA 寫入接口 |
| `lab` | GA 進化、回測、基因庫管理 | 禁止交易指令下發、實例只讀 |
| `dev` | 全部模組 | 無限制（僅本地開發） |

### 2.2 LocalAgent 的雙態：Paper / Live

LocalAgent 不是必要組件。當 `Instance.Mode = "paper"` 時，SaaS 直接走 `internal/broker/paper/`，**無需 Agent**。Live 模式才需要用戶部署 Agent。

```
Live  : SaaS → WebSocket → LocalAgent → Binance REST → DeltaReport → SaaS
Paper : SaaS → PaperBroker（in-process 模擬）→ 直接更新帳本
```

詳見 `30-Paper-Trade-模式.md`。

## 3. 邏輯模組與責任邊界

### 3.1 Strategy 模組（Application）
策略模板（圖紙）。每個策略實作 `internal/strategy.Strategy` 接口（見 `10-策略框架接口.md`）。回測與實盤共用同一個 `Step()`，**禁止內部分叉**。

### 3.2 Instance 模組（設備中心）
實例 = **策略模板 + 交易標的 + 資金配額 + 用戶授權 + Mode**。

實例狀態枚舉（4 態）：

| 狀態 | 語義 | 進入條件 | 離開條件 |
|------|------|---------|---------|
| `RUNNING` | 正常推進 | 用戶 Start，且 champion 存在（或策略不需 GA） | 用戶 Stop / 異常 / champion 消失 |
| `STOPPED` | 已暫停 | 用戶 Stop | 用戶 Start |
| `BLOCKED` | 等待 promote（無 champion） | `loadChampion` 回 `ErrNoChampion` | Promote 完成 → 自動轉 RUNNING |
| `ERROR` | 異常需介入 | 帳本不一致 / API 失敗 | 人工 reconcile + reset |

cron 掃描 `RUNNING` 與 `BLOCKED` 實例。`STOPPED` / `ERROR` 跳過。

### 3.3 Evolution & Backtest 模組（參數實驗室）
GA 進化引擎產出 `challenger` 基因包，人工審批晉升為 `champion`。**僅 `lab` / `dev` 模式可觸發**。

策略可以是「不進化」的（如 `simple-dca`）—— 此類策略沒有 challenger / champion，直接用 hardcoded params。

### 3.4 Broker 模組（執行抽象）
```go
type Broker interface {
    PlaceOrder(ctx, cmd TradeCommand, currentPrice float64) (Execution, error)
    GetBalances(ctx) ([]Balance, error)
}
```
- `internal/broker/binance/`：真實 broker（透過 LocalAgent WS 中繼）
- `internal/broker/paper/`：模擬 broker（in-process，C1 起步）

### 3.5 User / Auth 模組
JWT 簽發、訂閱配額守門。不涉及策略邏輯。

## 4. 全局狀態總線

### 4.1 單一 Postgres + 單一 Redis
- Postgres 資料庫名 `eighti_quant`，不分 Shell DB / Live DB
- Redis 僅作快取（冠軍基因 / Session / Paper 帳本暫存等），**不**承擔信號傳遞或事件佇列

### 4.2 資料真源與所有權

| 資料 | 真源 | 說明 |
|------|------|------|
| 策略決策邏輯 | `Step()` 實作（SaaS 側執行） | 回測與實盤共用 |
| 冠軍參數包 | SaaS DB `gene_records` | GA 產出，供實例綁定 |
| 終端用戶與訂閱 | SaaS DB | 統一管理 |
| 執行中實例狀態 | SaaS DB | DeltaReport 維護 |
| Binance API 憑證 | LocalAgent 本地 `config.agent.yaml` | 永不進入 SaaS DB |
| 成交記錄與資產快照 | SaaS DB | Agent 上報後持久化（live）/ PaperBroker 直寫（paper）|
| 歷史價格序列 | SaaS DB `market_data_points` | 只存 close + open_time（無 OHLCV）|
| GA 任務與基因紀錄 | SaaS DB | 單一資料庫 |

### 4.3 API Key 物理隔離鐵律
Binance API Key / Secret **只能**存在於 LocalAgent 本地 `config.agent.yaml`：
- 永不進入 SaaS 服務記憶體
- 永不寫入任何資料庫表
- 永不透過網路傳輸到雲端

Paper 模式不需要 Binance API Key。

### 4.4 MarketDataPoint 資料表（取代舊版 KLine）

```go
type MarketDataPoint struct {
    ID        uint   `gorm:"primaryKey"`
    Symbol    string `gorm:"uniqueIndex:idx_sym_int_open"`
    Interval  string `gorm:"uniqueIndex:idx_sym_int_open"` // "1h" / "4h" / "1d"
    OpenTime  int64  `gorm:"uniqueIndex:idx_sym_int_open"` // ms, UTC
    Close     float64
    // 注意：不存 Open/High/Low/Volume
    // 設計理由見 strategies/lunar-spot-v1.md（影片新版去 OHLCV 化）
}
```

**為什麼不存 OHLCV：**
- `lunar-spot-v1` 不需要（PVA 純粹基於 close）
- `simple-dca` 不需要（純定投，不看價格走勢）
- `grid` 不需要（用網格線判斷，只需 close）
- 未來如果有策略需要 OHLCV，再以新表 `market_data_ohlcv` 並列存放，**不破壞現有 schema**

策略可在 `Manifest.RequiredDataKind` 宣告需求：`"close-only"` 或 `"ohlcv"`。當前 reference 策略全部 `close-only`。

## 5. IoT 通訊協議（Live 模式）

Paper 模式跳過此節。

### 5.1 WebSocket 長連線模型

Agent 發起連線，SaaS 監聽 `/ws/agent`。連線後 Agent 必須先發 JWT 鑑權訊息。每 30 秒 heartbeat。

### 5.2 訊息類型

| 訊息 | 方向 | 觸發 |
|------|------|------|
| `auth` | Agent → SaaS | 連線建立 |
| `auth_result` | SaaS → Agent | 鑑權完成 |
| `heartbeat` / `heartbeat_ack` | 雙向 | 每 30 秒 |
| `command` | SaaS → Agent | Step() 產出意圖 |
| `command_ack` | Agent → SaaS | 收到 command |
| `delta_report` | Agent → SaaS | 成交完成 / 重連快照 |
| `report_ack` | SaaS → Agent | SaaS 處理完 |

### 5.3 TradeCommand 欄位

| 欄位 | 說明 |
|------|------|
| `client_order_id` | `inst{id}-{engine}-{action}-{barTimeMs}-{seq}` |
| `action` | `BUY` / `SELL` |
| `engine` | 由策略產出（如 `MACRO` / `MICRO` / `GRID`）|
| `symbol` | `BTCUSDT` 等 |
| `amount_usdt` | BUY 用 |
| `qty_asset` | SELL 用 |
| `lot_type` | `DEAD` / `FLOAT` / `COLD_SEALED`（見策略文件）|

### 5.4 DeltaReport 欄位
`balances`（資產+USDT 快照）+ `execution`（成交明細）+ `client_order_id`（重連快照可空）。

### 5.5 Reconcile 機制

#### 5.5.1 Agent 重連 4 場景

| 場景 | 處理 |
|------|------|
| A. 平靜斷線 | 走 §5.5.4 帳本一致性檢查；不等 → ERROR |
| B. SaaS 已下 / Agent 沒收到 | ReconcilePendings（§5.5.1.1）|
| C. Agent 已執行 / 沒回 | 同 B |
| D. 訊息順序錯亂 | 以 client_order_id 為主鍵；快照做 divergence 驗證 |

#### 5.5.1.1 ReconcilePendings 演算法

對每筆 pending，透過 Agent 呼叫 Binance：
```
GET /api/v3/order?symbol=&origClientOrderId=
  → status=NEW/PARTIALLY_FILLED → KeepPending
  → status=FILLED → 查 myTrades by orderId → MarkFilled
  → status=CANCELED/EXPIRED/REJECTED → 視 ExecutedQty 決定 MarkCanceled 或 MarkPartiallyFilledThenCanceled
  → 錯誤 -2013 (Order does not exist) → MarkCanceled
```

#### 5.5.1.2 Cancellation Compensation
- BUY canceled → 反向 mutate runtime（如 macro budget）
- SELL canceled + paired hard_release → lot 從 FLOAT 改回 DEAD
- 必須與 pending status 變更**同 transaction**

#### 5.5.2 Tick 前 Pending 預檢
每個 cron tick 在呼叫 `Step()` **之前**：
- 有 pending → 觸發 ReconcilePendings；仍未終態 → 跳過此 tick
- 無 pending → 進 Step()

**設計理由**：寧可慢一個 tick，不可重複下單。

#### 5.5.3 SaaS 重啟恢復
Load `RUNNING` + `BLOCKED` 實例 + 所有 `pending SpotExecution`（無時間上限）。**取消「30 分鐘自動 expired」**。

#### 5.5.4 Lot vs Balance 一致性檢查
重連快照後驗證 `SUM(lots by type) == snapshot balances`（容差 LotMinQty）。不等 → instance state = ERROR。

## 6. 系統級生命週期動作

### 6.1 系統初始化
1. 讀 config.yaml、初始化 DB / Redis / JWT
2. GORM AutoMigrate（所有 model）
3. 執行 `internal/saas/store/indexes.sql`（partial unique index）
4. 偵測 duplicate champion preflight（見 `20-進化計算引擎.md` §6.2.1）
5. Load `RUNNING` + `BLOCKED` 實例
6. 啟動 WS Hub / cron / HTTP server

### 6.2 Cron Tick 主流程

```
# Phase A: 前置安全閘（任一失敗即 return）
1. loadChampion（version-aware read-through，見 20- §6.2.2）
   - ErrNoChampion → 標 BLOCKED + audit + return
   - 策略不需 GA → 從 strategy.DefaultParams() 取
2. 同 bar 去重檢查（LatestBarTimeMs vs LastProcessedBarTime）
3. Pending 預檢（§5.5.2）
4. Lot vs Balance 一致性檢查（§5.5.4）

# Phase B: Step()
5. 從 SaaS DB 拉 MarketDataPoint（≥ 策略宣告的 warmup bar 數）
6. 從 Broker 拉即時 ticker price（Live 走 Agent，Paper 走 PaperBroker）
7. 建構 StrategyInput（含 closes 序列、Portfolio、ticker price、LatestBarTimeMs）
8. 呼叫 strategy.Step()

# Phase C: 原子持久化
BEGIN TX:
  9. Intents 翻譯為 TradeCommand 並生成 client_order_id
     建立 index → client_order_id 對照表（intentClientIDs[i] = generated_cmd_id）
  9.5. Releases 用 RelatedIntentIndex 解析對應的 client_order_id：
       for each release in output.Releases:
         if release.Kind == "hard_release":
           release.RelatedClientOrderID = intentClientIDs[release.RelatedIntentIndex]
       （soft_release 的 RelatedIntentIndex = -1，跳過此步）
  10. 寫 pending SpotExecution（含 client_order_id）
  11. 持久化 NewRuntime
  12. 處理 Releases（DEAD↔FLOAT 帳本轉換 + 寫 RelatedClientOrderID 到 audit log，
      供 cancellation compensation 配對 rollback）
  13. 寫 audit log
  14. 更新 LastProcessedBarTime
COMMIT TX

# Phase D: 派單
15. Live 模式：WS 下發給 Agent
    Paper 模式：呼叫 PaperBroker.PlaceOrder() → 直接模擬成交 → 寫 DeltaReport
```

### 6.3 Agent 斷線重連（Live 模式）
指數退避 1s → 5min；重連時送初始快照觸發 reconcile。

### 6.4 優雅停機
SIGTERM → 停 cron → 等 tick 完成（30s timeout）→ 持久化 runtime 快照 → 關閉 WS / DB / Redis。

## 7. 不可推翻的技術決策

1. **策略同構**：回測 = 實盤共用 `Step()`，禁止 `if isBacktest`
2. **策略純函數**：禁網路 / DB / 檔案 / 計時器 / 隨機
3. **API Key 物理隔離**：見 §4.3
4. **GORM Code-First + indexes.sql 例外**：見 `CLAUDE.md` §2.4
5. **無量綱計算**：跨標的禁用絕對價格
6. **單一 Postgres**：不分庫；Redis 僅快取
7. **Paper / Live 同構**：兩種模式跑同一個 `Step()`
8. **Strategy 可抽換**：增刪策略不影響 framework core
9. **Framework 不感知策略**：`internal/saas/ga/engine.go` 等 framework 程式碼**禁止 import** `strategies/` 任何包
