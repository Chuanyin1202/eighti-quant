# 進化計算引擎

**文件目標：** 將進化系統降維為一個純粹的尋優黑盒。進化引擎不關心具體策略內部結構，只透過抽象接口驅動種群生命週期。具體策略的染色體欄位、邊界、適應度語義由策略模組在 `策略數學引擎.md` 中定義。

---

## 0. 核心定位

進化引擎是一個**純計算執行緒**：接收策略提供的基因空間與評估函數，對種群執行多代進化，交付最優基因集（Champion）。

引擎不關心：策略內部的訊號公式、倉位三態語義、特定時鐘機制，也不 import 任何具體策略實作。引擎只知道：基因是一個可採樣、可變異、可交叉、可評分的抽象向量。

**輸入：** 策略提供的基因空間（邊界、約束）+ 歷史 K 線數據集 + 進化配置參數
**輸出：** 挑戰者（challenger）基因包 JSON，寫入資料庫，等待人工 Promote 為冠軍

---

## 1. 探索窗口定義

### 1.1 數據切片窗口（多時段坩堝）

Epoch 啟動時，引擎一次性從資料庫拉取**本 Epoch 所需的全部** 4h K 線序列用於建構坩堝：**不對全庫長度設「最多十年」等人工上限**；能有多長取決於上游已同步入 Postgres 的數據，下限以 **Binance 側可拉取到的最早可用 bar** 為準（BTCUSDT 約 2017-08，ETHUSDT 約 2017-08）。

在此基礎上建構以下四個滾動窗口（標識「10y」表示長週期檔，**評分區間取入庫全序列**——自最早可用 bar 至最新 bar，不設人工天數上限）。

| 窗口標識 | 目標時長（評分截取區間） | 適應度權重 |
|---------|---------|---------|
| 10y | 全量（最早至最新 bar） | 0.40 |
| 5y | 1825 天 | 0.30 |
| 2y | 730 天 | 0.20 |
| 6m | 183 天 | 0.10 |

**目標時長說明：** 5y / 2y / 6m 為對齊最新一根 bar 的最近若干日歷日，並在該截取區間之前再預留最多 1200 天 warmup K 線（用於指標預熱，不計入評分區間）。**10y 檔不再單獨截斷為固定天數**，直接使用本 Epoch 傳入的 `bars` 全序列；若序列長於十年，則長週期評分自然覆蓋更長歷史。更短窗口仍使用同一全庫序列中的尾部片段及各自 warm-up 前綴。

**嚴禁未來數據洩露：** 每個窗口的評估區間從 `EvalStartMs` 開始，warmup 數據必須在 `EvalStartMs` 之前。

### 1.2 基因空間窗口

策略透過以下語義向引擎提供基因邊界，引擎不直接讀取欄位名：

- **採樣（Sample）：** 從合法空間隨機生成一個基因實例
- **修復（Clamp）：** 將越界基因修復到合法範圍（含結構約束修復）
- **驗證（Validate）：** 檢查基因是否合法

### 1.3 出生點凍結窗口（Epoch 級）

`quant.SpawnPoint`（`CapitalPolicy` + `RiskBounds`）在 Epoch 啟動時固定，全種群共享；不參與代內交叉變異，不進入基因組指紋。

`POST /api/v1/evolution/tasks` 支援 `spawn_mode`：
- `inherit`：繼承當前 champion 的 SpawnPoint，無 champion 則用系統預設
- `random_once`：排隊時抽樣一次並凍結（整個 Epoch 共享）
- `manual`：請求體填寫 `spawn_point` JSON

引擎經 `EpochConfig.SpawnPointOverride` 注入 `internal/saas/ga`。

## 2. 進化生命週期動作

### 2.1 種群初始化

種群大小預設 `Population = 300`，初始化策略：

**當資料庫中存在精英基因時：**
- **10%**：從資料庫精英中原樣拷貝
- **40%**：在精英基礎上施加加性高斯強化變異（初始化路徑固定變異概率 `0.15`、尺度 `1.5`，與代內 `MutationRamp` 無關）
- **50%**：完全隨機生成

**當資料庫無精英時：** 第一個體為產品預設冠軍染色體原樣，其餘個體完全隨機生成。

**實作約定：**
- 索引 0 始終為當前種子冠軍原樣（有 DB 精英則為庫中冠軍染色體，否則為產品預設冠軍 `DefaultSeedChromosome`）
- 僅對索引 1 起的剩餘個體按上表約 10% / 40% / 50% 計數分配（相對剩餘個體數四捨五入）
- 無 DB 精英時索引 1 起全部為 `RandomChromosome`

### 2.2 並發適應度評估

評估採用固定大小 worker pool 並發執行：

```
Workers = min(NumCPU, PopulationSize)
```

每個 worker 獨佔一份 Adapter 實例（回測上下文），無共享可變狀態。所有 worker 並發處理任務佇列，等所有任務完成後進入下一代。

### 2.3 選擇（錦標賽 Tournament）

每次選擇從種群中隨機抽 `TournamentSize`（預設 3）個個體，取適應度最高者為父代。適應度為 `fatalFitnessScore`（災難性極小值 `-99999`）的個體在錦標賽中自然被淘汰（無需顯式排除，因 fatal 個體分數極低）。

### 2.4 交叉（Uniform Crossover）

對每個基因維度以 0.5 概率獨立地從兩個父代中選取，生成子代。引擎不關心欄位語義，由策略的 `Clamp` 邏輯在交叉後修復結構約束。

`uniformCrossoverWithMode` 對所有維度獨立 50% 交換，結構約束修復在交叉後呼叫 `repairGeneWithMode`。**宏觀/微觀塊正交交叉為 [規劃，未實作]**。

### 2.5 變異（加性高斯）

每個基因維度以獨立 Bernoulli 概率 `MutationProbability`（預設 0.15）決定是否變異；變異量為 `NormFloat64() × GeneStep × MutationScale`（預設 Scale=1.0）。變異後呼叫 `Clamp` 修復越界值。

### 2.6 精英保留（Elitism）

每代保留適應度 Top `Elitism`（預設 8）個個體，不經交叉變異直接入下一代。

### 2.7 收斂偵測與變異斜坡（Mutation Ramp）

連續 `EarlyStopPatience`（預設 5）代內最佳適應度改善低於 `EarlyStopMinDelta`（預設 0.001）時，觸發變異斜坡：

```
MutationProbability *= MutationRampProbFactor   (1.25)
MutationScale       *= MutationRampScaleFactor  (1.25)
```

上限：`MutationProbabilityMax = 0.55`，`MutationScaleMax = 3.0`

當變異參數觸及上限後仍無改善，才真正提前終止（Early Stop）。

### 2.8 Genome 指紋快取（Fingerprint Cache）

策略提供 `Fingerprint`（指紋）語義（對基因向量按精度 1e-6 做 FNV-1a-64 雜湊），引擎在 Epoch 內偵測重複個體，命中快取則複用評估結果，跳過重複回測。預期命中率約 15–30%（來自精英保留產生的重複）。

### 2.9 收斂交付

進化結束後（正常完成或 Early Stop），將最優基因包編碼為 JSON（`EncodeResult`），寫入資料庫為 `challenger` 角色。**進化任務不自動 Promote**，必須等待人工審批。

## 3. 適應度黑盒（Fitness Function）

### 3.1 多窗口坩堝分數

對每個切片窗口，以策略的累計回報相對於 Ghost DCA 基準計算 Alpha，再按超額回撤懲罰：

```
Alpha       = ROI_strategy - ROI_GhostDCA
SliceScore  = Alpha - DDPenaltyCoef × max(0, MaxDD_strategy - MaxDD_GhostDCA)

預設 DDPenaltyCoef = 1.5（可由 EpochConfig 覆蓋）
```

**Window-Local Fatal + Recency-aware Penalty**：

當 `MaxDD_strategy >= FatalDDThreshold[window]` 時，按 window 距離當下時間的近遠決定懲罰強度：

| Window | FatalDDThreshold | SliceScore_fatal | 原因 |
|--------|------------------|------------------|------|
| **6m** | 0.50 | **-200** | 最近 6 個月內 50%+ 回撤是「現在還在賠錢」的訊號，必須 block |
| **2y** | 0.75 | **-100** | 近 2 年內 75%+ 回撤代表近期適應性差，重罰 |
| **5y** | 0.88 | -10 | 5 年大跌通常包含完整熊市，不該完全否決 |
| **10y** | 0.95 | -10 | 10y 含早期歷史，閾值最寬鬆 |

預設可由 `EpochConfig.FatalDDThresholds` 與 `EpochConfig.FatalPenalties` 覆蓋。

**為什麼用 window-specific 閾值與懲罰：**

第一輪修補時用「全 window 共用 -10 懲罰」，審查發現：worked example 中「只 6m fatal」總分 -0.20 仍可通過 tournament，**剛剛 92% drawdown 的個體也可能被 promote**。這是不可接受的 live trading 風險。

修正後：
- **6m / 2y window 的 fatal 是 blocking** —— -200 / -100 的 penalty 加上 0.10 / 0.20 weight，單一 window fatal 即可把總分拉到 -20 / -20 量級，無法被舊 window 救活
- **5y / 10y window 的 fatal 是 soft penalty** —— BTC 歷史 5y/10y MaxDD 經常碰 80%+，太嚴會把所有個體都打 fatal

**Worked Examples（必須 unit test 對得上）：**

| 場景 | Score_10y | Score_5y | Score_2y | Score_6m | ScoreTotal |
|------|-----------|----------|----------|----------|------------|
| 4 窗口都 fatal | -10 | -10 | -100 | -200 | 0.40×-10 + 0.30×-10 + 0.20×-100 + 0.10×-200 = **-47.0** |
| 只 10y fatal | -10 | 0.5 | 0.5 | 0.5 | -10×0.40 + 0.5×0.60 = **-3.70** |
| 只 6m fatal | 1.0 | 1.0 | 0.5 | -200 | 1.0×0.70 + 0.5×0.20 + (-200)×0.10 = **-19.20** |
| 只 2y fatal | 1.0 | 1.0 | -100 | 0.5 | 1.0×0.70 + (-100)×0.20 + 0.5×0.10 = **-19.25** |
| 全綠（無 fatal） | 1.0 | 0.8 | 0.5 | 0.3 | **0.78** |

近 window fatal 個體（-19 量級）與正常個體（>0）有壓倒性落差，tournament 不可能選中。

**設計理由（為什麼不用 -99999 全局硬否決）：**

審查發現 BTC 歷史 drawdown 經常在 70-90% 區間（2018: -84%, 2022: -77%），Ghost DCA 自己在 10y 上 MaxDD 會接近 88%。若採全局硬否決，**baseline 自己都會 fatal**，且把所有「能持有底倉跑贏 DCA 的策略」全部淘汰，GA 只剩「持倉很輕、與 DCA 高度相似的退化解」 —— 違反複利前置鐵律。

Window-local fatal 的好處：
- 6m 短期 fatal 不會把 10y 長期高分強制歸零
- 各 window 仍貢獻獨立資訊
- 重罰但不足以讓所有 fatal 個體在 tournament 中分數都打平 → 仍有梯度區分

各窗口加權匯總（單純加權和，無短路、無 sentinel）：

```
ScoreTotal = 0.40 × Score_10y + 0.30 × Score_5y + 0.20 × Score_2y + 0.10 × Score_6m
```

實作 `Evaluate()` 時，**至少**用前述（5 組）case 寫單元測試。

**Tournament 區分性：** 近 window fatal 個體（≤ -19）與正常個體（>0）有壓倒性落差。tournament size=3 隨機抽 3 個都 fatal 機率即使在早期高 fatal 率世代也不會選出 fatal 個體晉升至 promotion 名單。

### 3.2 Ghost DCA 基準（Per-tick DCA，與策略 Macro 引擎完全對齊）

`SimulateGhostDCA` 以種子資本（`SpawnPoint.Policy.InitialCapitalUSDT`）買入標的資產，然後採用**每 4h bar 均勻買入**節奏作為被動 DCA 基準：

```
BarsPerDay = 24 / 4 = 6
PerTickBudget(t) = MonthlyInjectUSDT / (DaysInMonth(t) × BarsPerDay)

每個完整的 4h bar 收盤觸發一次買入 PerTickBudget(t) USDT
（DaysInMonth 隨當前 bar 所屬月份動態決定，避免跨月時的月度天數差）
```

**設計理由（為什麼從 daily 改為 per-tick）：**

第一輪修補時把月初一次買改為 daily DCA，但策略 Macro 引擎的預算粒度是 per-tick (4h)，**baseline 仍跑 daily 與策略 cadence 不一致**：策略一天可在 6 個 4h bar 各自反應，baseline 只買一次。GA 仍可透過「在 4h bar 抓 baseline 沒覆蓋的時點」獲得偽 alpha。

改為 per-tick 後：
- baseline 與策略 Macro 引擎共用同一個時鐘（每 4h 觸發）
- baseline 與策略 Macro 共用同一個預算量綱（每 tick 買 `MonthlyInject / (Days × 6)`）
- GA 必須真正透過動態加速 / 死線兜底產生超額收益才能跑贏 baseline，無法靠時序錯配偽造

**注：** 這裡的「DCA baseline」純粹用於 GA 適應度評估，不代表「最佳的真實 DCA 策略」。實際用戶使用 daily 或 monthly DCA 均可，文件層面明確此 baseline 選擇是為了**對齊評估時序**。

策略個體必須跑贏此基準（`Alpha > 0`）才算有效。

注資節奏：每 4h bar 買 `MonthlyInjectUSDT / (DaysInMonth × 6)` USDT，與策略 Macro 引擎 §4.3 的 `PerTickBase` 公式一致（差別僅在策略受 `TimeDilation` 與 `MacroAccelerator` 加速、baseline 不加速）。

### 3.3 ROI 計算

策略的 ROI 採用「**Modified Dietz 收益率**」思路，剔除注資跳變對 NAV 的影響（注資時刻的權益變化不計入收益）。NAV 最大回撤基於淨資產曲線計算。

```
ROI = (期末權益 - 期初權益 - Σ(現金流_i)) /
      (期初權益 + Σ(現金流_i × 加權因子_i))

加權因子_i = (總天數 - 注資發生日_i) / 總天數
```

### 3.4 評估順序（無短路）

適應度評估**全部 4 個窗口都跑完**，沒有級聯短路。

審查發現原本的「6m → 2y → 5y → 10y 短路 + 0.40 權重在 10y」設計與目標函數背道而馳：早期世代 6m 易 fatal，會讓 GA 永遠摸不到 10y 高權重個體；short-circuit 的算力收益被「最重要的 10y 從未真正評估」抵銷。

實作上仍按短到長順序跑（`6m → 2y → 5y → 10y`），方便監控進度與早期偵錯，但不在中途返回。

## 4. 性能優化機制

以下優化已在當前實作中落地：

**4.1 並發評估：** Genome 粒度 worker pool，CPU 數量上限（見 §2.2）。
**4.2 Tournament fatal 排除：** Window-local fatal 個體 ScoreTotal 區間 [-10, 0]，與正常個體（區間通常 [-1, 2]）有明顯落差，tournament 自然淘汰；早期世代若 fatal 率 > 50% 時建議顯式過濾（見 §2.3 變體實作）。
**4.3 Genome Fingerprint 快取：** 命中率約 15–30%（見 §2.8）。

以下優化屬於**規劃，未實作**：

**4.4 Nested Replay（巢狀重播）：** 一次全樣本回測 + 各窗口 EvalStart checkpoint 差分，將 4 次獨立回測合併為 1 次。取消短路後，這個優化的價值上升（不再有「6m fatal 跳過長窗口」的衝突），但實作複雜度高，當前 Phase 不做。
**4.5 前綴和 O(1) 滑窗統計 + EMA 增量化：** 減少每次適應度評估中的重複統計計算。
**4.6 蒙特卡洛異步化：** Epoch 驗證階段的 MC 採樣並行化，主執行緒等待結果。

## 6. 結果交付與基因角色

### 6.1 基因角色三態

資料庫中的基因紀錄有三種角色，形成狀態機：

| 角色 | 含義 |
|------|------|
| `challenger` | 進化產出，等待人工審批 |
| `champion` | 當前活躍冠軍，驅動實盤實例 |
| `retired` | 歷史冠軍，僅供查閱與回溯 |

### 6.2 人工 Promote 流程

進化任務產出 `challenger` 後，操作員在前端查看回測報告與風險指標，決定是否晉升。

#### 6.2.1 事務協議（防競態 + 防 split-brain）

```
BEGIN; -- 事務隔離級別: REPEATABLE READ

-- 1. 取得 advisory lock（即使無現任 champion 也能序列化 promote）
--    key 由 (strategy_id, symbol) 哈希得到，唯一對應這條 promote 通道
SELECT pg_advisory_xact_lock(
    hashtextextended('promote:' || ? || ':' || ?, 0)
);
-- 註：advisory lock 在事務 commit/rollback 時自動釋放

-- 2. 退役當前 champion（若無 row，UPDATE 影響 0 行，正常繼續）
UPDATE gene_records
  SET role = 'retired', retired_at = NOW()
  WHERE strategy_id = ? AND symbol = ? AND role = 'champion';

-- 3. 晉升 challenger（必須驗證該 challenger 仍是 challenger）
UPDATE gene_records
  SET role = 'champion', activated_at = NOW()
  WHERE id = ? AND strategy_id = ? AND symbol = ? AND role = 'challenger';
-- 若影響 0 行（被別人改了）→ ROLLBACK 並回報錯誤

-- 4. 寫審計日誌
INSERT INTO audit_logs (event_type, payload) VALUES ('promote', ?);

COMMIT;

-- 5. 事務 commit 成功後才刪 Redis cache（cache-aside 模式）
DEL champion:{strategy_id}:{symbol}
```

**advisory lock 的關鍵作用：**

原本只用 `FOR UPDATE` 鎖 `role='champion'` 的 row → **無現任 champion 時鎖空**（bootstrap 狀態、災難復原後、或前次 promote 異常半完成），兩個並發 promote 會同時通過、創建 split-brain（同 (strategy_id, symbol) 多個 champion）。

advisory lock 鎖的是「邏輯通道」（`promote:{strategy}:{symbol}` 的哈希值）而非具體 row，**無 row 也能鎖**。即使在 zero-champion 狀態，兩個並發 promote 也會被序列化。

**事務 commit 成功後再刪 cache** 的順序避免 race window：若先刪 cache 再 commit，cache 失效但 DB 還是舊冠軍 → cron tick 讀 DB 拿到舊冠軍寫回 cache → 新 cache 內容仍是舊冠軍 → 新冠軍永遠生效不了。

#### 6.2.1.1 Partial Unique Index（DB 層級兜底防線）

advisory lock 是應用層協議，**DB 層級必須額外有 partial unique index** 作為最後防線：

```sql
CREATE UNIQUE INDEX IF NOT EXISTS uniq_active_champion
ON gene_records (strategy_id, symbol)
WHERE role = 'champion';
```

此 index 在「同 (strategy_id, symbol) 出現第二個 `role='champion'` 紀錄」時會 INSERT/UPDATE 直接失敗，無論應用層協議是否被繞過。

**安裝路徑（唯一路徑，必須照做）：**

此 partial index **必須**寫入 `internal/saas/store/indexes.sql`，由 `db.go` 在 AutoMigrate 完成後 `db.Exec(ddl)` 執行。**禁止**透過任何其他方式（migration `.sql`、手動 `psql`、運維手動執行）建立此 index。

完整契約見 `CLAUDE.md` §2.4.2。`indexes.sql` 內容必須：
- 用 `CREATE UNIQUE INDEX IF NOT EXISTS` 確保可重複執行
- 變更時走 PR review，不允許跳過 code review 直接動 production DB

#### 6.2.2 Cron tick 對 champion 的取用協議（Version-aware Read-through）

**設計原則：不存在 in-process champion cache。** 每個 cron tick 開頭從 Redis 讀取 champion，並用 DB 上的 `activated_at` 做版本驗證（避免 Redis 失效或 DEL 失敗時 worker 仍跑舊 champion）。整個 tick 用同一份快照，**禁止**在 `Step()` 過程中重新 fetch。

```
func (m *InstanceManager) Tick(instanceID uint) {
    champion, err := m.loadChampion(strategyID, symbol)
    if err == ErrNoChampion {
        // §6.2.3 zero-champion 路徑：跳過此 tick + 標記實例 BLOCKED
        m.markBlocked(instanceID, "no champion available")
        m.audit.Log(instanceID, "tick_skipped_no_champion", nil)
        return
    }
    if err != nil {
        m.log.Error("loadChampion failed", "err", err)
        return  // 暫時跳過，下次 tick 再試
    }
    runtime  := m.db.Load(instanceID)
    output   := strategy.Step(input, champion.Params)
    m.persist(output, runtime)
}

var ErrNoChampion = errors.New("no champion available for (strategy, symbol)")

func (m *InstanceManager) loadChampion(strategyID, symbol string) (*Champion, error) {
    key := fmt.Sprintf("champion:%s:%s", strategyID, symbol)

    // 1. 從 DB 拉「當前 champion 的 ID + activated_at」（輕量索引查詢）
    //    這是 source-of-truth 版本標記。每 4h tick 一次的開銷可忽略。
    var head struct {
        ID          uint
        ActivatedAt int64  // unix ms
    }
    err := m.db.Model(&GeneRecord{}).
        Select("id, activated_at").
        Where("strategy_id = ? AND symbol = ? AND role = 'champion'", strategyID, symbol).
        First(&head).Error

    // 1a. zero-champion 路徑（bootstrap / disaster recovery）
    if errors.Is(err, gorm.ErrRecordNotFound) {
        return nil, ErrNoChampion
    }
    if err != nil {
        return nil, fmt.Errorf("query champion head: %w", err)
    }

    // 2. 嘗試從 Redis 拿完整 champion + 版本
    if cached, gerr := m.redis.Get(key); gerr == nil {
        c := decodeChampion(cached)
        // 3. 版本驗證：cache 的 activated_at 必須等於 DB head 的版本
        if c.ID == head.ID && c.ActivatedAt == head.ActivatedAt {
            return c, nil  // 版本一致，cache 命中
        }
    }

    // 4. DB fallback（cache miss / 版本不一致 / Redis 故障）
    var rec GeneRecord
    if ferr := m.db.Where("id = ?", head.ID).First(&rec).Error; ferr != nil {
        return nil, fmt.Errorf("load champion record: %w", ferr)
    }
    c := buildChampion(&rec)

    // 5. 寫回 Redis（best-effort，TTL 24h；失敗只 log，不阻塞 tick）
    if serr := m.redis.SetEx(key, encodeChampion(c), 24*time.Hour); serr != nil {
        m.log.Warn("redis champion cache writeback failed", "err", serr)
    }
    return c, nil
}
```

**版本驗證是核心修正：**

審查發現「只刪 Redis、靠 TTL 24h 兜底」的設計在 DEL 失敗時讓舊 champion 跑最長 24 小時。**改為 version-aware read-through 後，即使 Redis DEL 100% 失敗，下次 tick 仍會偵測到 cache 中 `activated_at` 與 DB head 不符，強制走 DB 路徑並更新 cache**。

**版本驗證的成本：**
- 每 tick 多一次 DB 查詢，但只 SELECT 2 個欄位（id, activated_at）+ 走 partial unique index `uniq_active_champion`，是 O(log N) 的索引查詢
- 4h K 線 tick 頻率：每實例每 4h 一次。雙標的雙實例 = 每 4h 共 2 次查詢。可忽略

**Redis 不可用時的退化行為：**
- `Redis.Get` 失敗 → 直接走步驟 4 DB 路徑
- `Redis.SetEx` 失敗 → log warn，但不阻塞 tick；下次 tick 會再嘗試
- 4h tick 頻率下 cache miss 完全可承受

**為什麼禁止 in-process cache：**

in-process cache 引入「promote 後 worker 不會自動更新」的問題：promote 只 `DEL` Redis，process 內若有獨立 cache 仍是舊 champion 直到重啟。**取消 in-process cache 後，所有 worker 共用 Redis + DB head 版本，DEL 成功 OR DEL 失敗都能在下一 tick 強制更新到新 champion**。

**`promote` 後的生效時間保證：**

- DEL 成功路徑：下一 tick 即生效（≤ 4 小時）
- DEL 失敗路徑：下一 tick 偵測到版本錯位 → 強制 DB refresh → 生效（仍 ≤ 4 小時）
- 任一情境**都不會超過一個 4h tick 延遲**，無需依賴 24h TTL 自然過期

#### 6.2.3 SpawnPoint 切換的 RuntimeState 處理

新 champion 的 SpawnPoint（含 `MonthlyInjectUSDT`）若與舊 champion 不同：
- `RuntimeState.Macro.MonthlyBudget` 在下一個自然月初**重置**為新 SpawnPoint 的 `MonthlyInjectUSDT`
- 當前月內仍按 `RuntimeState.Macro` 中已有的 `MonthlyBudget` 跟 `SpentThisMonth` 跑（不立即重置，避免月中行為跳變）
- 此規則在 `策略數學引擎.md` §4.2 描述

#### 6.2.3 Zero-champion 狀態處理（Bootstrap / Disaster Recovery）

§6.2.1 advisory lock 明確處理「並發 promote 在 zero-champion 狀態下不能 split-brain」，但執行端 `loadChampion` 也必須有對應路徑：當 `(strategy_id, symbol)` 沒有 `role='champion'` 紀錄時，**禁止**用空值或 fallback 跑 `Step()`，必須觸發**實例 BLOCKED**。

**Zero-champion 場景：**
1. 全新部署 — 還沒進化過第一個 champion
2. 災難復原 — DB 還原到「上次 promote 之前」的時點，舊 champion 已 retired 但新 champion 尚未產生
3. 手動 retire — 運維操作把當前 champion 退役但尚未 promote 新 challenger

**處理規則：**
- `loadChampion` 回傳 `(nil, ErrNoChampion)`
- 上層 `Tick()` 偵測到 `ErrNoChampion` → 跳過此 tick，**不**進入 `Step()`
- 將 instance state 標記為 `BLOCKED`（新增狀態，與 `ERROR` 區分：BLOCKED 表示「等待人工 promote」、ERROR 表示「異常需介入」）
- 寫 audit log `event_type=tick_skipped_no_champion`
- 前端 Dashboard 對 BLOCKED 實例顯示「等待參數審批」提示，引導用戶到 Evolution 頁面 promote challenger

**實例離開 BLOCKED 的條件：**
- Promote 完成、新 champion 寫入 DB → 下次 cron tick `loadChampion` 成功 → instance state 自動轉回 `RUNNING`
- 此自動轉回需要 `Tick()` 在 `loadChampion` 成功後檢查當前 state 並更新

**測試覆蓋（必須有單元測試）：**
1. `bootstrap_no_champion`：DB 完全空的情境下啟動實例 → tick 跳過、instance BLOCKED
2. `recovery_after_retire`：當前 champion 被退役、無新 champion → tick 跳過、instance BLOCKED
3. `recovery_then_promote`：BLOCKED 實例後續 promote → 下次 tick 成功 load 新 champion → instance 自動 RUNNING

### 6.3 規劃但未實作（當前 Epoch 不含）

## 7. HTTP 觸發契約（最小集合）

進化任務透過 REST API 觸發，**僅在 `app_role: lab` 或 `dev` 下可用**。

### 7.1 建立進化任務

`POST /api/v1/evolution/tasks`

參數：
- `pop_size`：種群大小，預設 300，範圍 [10, 500]
- `max_generations`：最大代數，預設 25，範圍 [5, 50]
- `strategy_id`：必填，例如 `lunar-spot-v1`
- `symbol`：必填，例如 `BTCUSDT` 或 `ETHUSDT`（雙標的各自獨立進化）
- `spawn_mode`：可選，`inherit` | `random_once` | `manual`；`manual` 時須帶 `spawn_point`（JSON，與 `quant.SpawnPoint` 對齊）
- `test_mode`：可選，快速測試模式，Pop=10, Gen=3

### 7.2 查詢任務狀態與結果

`GET /api/v1/evolution/tasks`

返回當前進化任務狀態（是否運行中）、歷次 challenger 基因列表（含 `ScoreTotal`、`MaxDrawdown`、各窗口分數）。

### 7.3 人工晉升

`POST /api/v1/evolution/tasks/:taskID/promote`

DB 事務內：當前 champion → retired，指定 challenger → champion；然後刪除 Redis champion 快取 key。

### 7.4 冠軍查詢

`GET /api/v1/genome/champion?symbol=BTCUSDT`

返回當前冠軍基因包（按標的查詢），優先從 Redis 快取讀取，cache miss 則從 DB 載入並寫入快取。

## 8. EvolvableStrategy 抽象接口

進化引擎透過此接口與具體策略完全解耦，`engine.go` 不含任何策略特有的染色體欄位名或型別引用。

### 8.1 八動詞契約

| 動詞 | 職責 |
|------|------|
| `StrategyID()` | 返回策略唯一標識符（例：`lunar-spot-v1`） |
| `Sample(rng)` | 從合法基因空間隨機採樣一個基因 |
| `Mutate(c, prob, scale, rng)` | 對基因施加加性高斯變異 |
| `Crossover(p1, p2, rng)` | 對兩個父代執行交叉，產出子代 |
| `Fingerprint(c)` | 返回基因的唯一雜湊（FNV-1a，精度 1e-6） |
| `Evaluate(ctx, c, plan)` | 在給定坩堝計畫上評估基因，返回適應度與各窗口明細 |
| `DecodeElite(json)` | 從 DB ParamPack JSON 解碼精英基因；`null` 時返回預設種子 |
| `EncodeResult(c, spawn)` | 將冠軍基因與出生點序列化為 ParamPack JSON（`spawn_point` + `lunar_spot_v1_config`） |
| `Verify(ctx, c, spawn, bars, lotStep, lotMin)` | 驗證路徑全量回測（含 Monte Carlo），返回 `BacktestMetrics` |

`Gene = any`：引擎持有不透明載體，不讀取內部欄位。

### 8.2 EvaluablePlan 只讀上下文

`EvaluablePlan` 在 Epoch 啟動時由 `buildEvaluablePlan` 建構，在整個世代內不可變，傳遞給所有 `Evaluate` 呼叫：

```
EvaluablePlan
├── Pair, TemplateName           // 標的（BTCUSDT/ETHUSDT）與模板標識
├── Spawn *quant.SpawnPoint      // 出生點（共享）
├── LotStep, LotMin              // 下單精度
├── Windows []CrucibleWindow     // 4 個切片窗口（含 K 線與權重）
├── DCABaselines []DCABaseline   // 預計算的 ghost-DCA 基線（與 Windows 一一對應）
└── AggregateCache               // 預聚合指標快取（可選）
```

DCA 基線在 Epoch 啟動時一次性計算，代內各染色體評估直接讀取，不重複執行 DCA 回測。

### 8.3 引擎對染色體內部欄位不可見原則

`engine.go` 透過八個動詞操作 `Gene`，對染色體欄位名完全不可見。新增策略只需實作 `EvolvableStrategy` 接口，無需修改引擎程式碼。

### 8.4 包位置約束（導入循環）

`LunarSpotV1Evolvable` 實作（含 `RunLunarSpotV1SingleBacktest`）位於 `internal/saas/ga/lunar_spot_v1_evolvable.go`，**而非** `internal/strategies/lunar-spot-v1/`。

原因：
- `backtest → lunar-spot-v1`（`adapter.go` 使用策略的 `Params`）
- `genome → lunar-spot-v1`（`store.go` 使用 `lunar.StrategyID`）

若將 `LunarSpotV1Evolvable` 放入策略包，則策略包須導入 `ga` 與 `backtest`，形成雙重循環依賴。將其放在 `ga` 包內則無新循環（`ga` 已依賴策略包，為單向依賴）。
