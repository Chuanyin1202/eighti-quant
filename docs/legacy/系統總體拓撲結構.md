# 系統總體拓撲結構

**文件目標：** 定義 EightiQuant 全局有哪些物理端、有哪些邏輯模組、狀態如何在它們之間流轉，以及系統整體的生命週期動作。**不含任何具體策略公式**（策略公式見 `策略數學引擎.md`）。

---

## 0. 架構哲學：時空正交與無記憶解算

**動作原則：** 所有業務推進必須被封裝為離散的「動作」，動作之間嚴禁隱式狀態傳遞（禁止「欠債紀錄」）。每個動作讀入當前狀態快照，產出新的確定性意圖，不依賴上一動作的記憶體變數。

**窗口原則：** 每個模組只能讀取屬於自己的「資料窗口」和「資金窗口」。策略模組看不到資料庫內部狀態，宏觀引擎看不到微觀的浮倉細節，進化引擎看不到實盤帳戶。

## 1. 主線設定（本專案的具體選型）

| 項目 | 選型 |
|------|------|
| 交易所 | **Binance 現貨**（Spot REST API v3） |
| 主線交易對 | **BTCUSDT** + **ETHUSDT** 雙標的 |
| 策略代號 | `lunar-spot-v1` |
| 聚合週期 `t_micro` | **4 小時 K 線** |
| 基礎掃描頻率 | cron 每分鐘 |

**雙標的設計原則：** 每個 Instance 只綁定一個標的（`BTCUSDT` 或 `ETHUSDT`），各自獨立跑 GA、各自有 champion 染色體。系統不做「跨標的訊號合成」，也不做「全幣種掃描」（後者屬於 Phase 14+ 外掛模組）。

## 2. 三端物理部署形態

### 2.1 SaaS 管理端（雲端，`app_role: saas`）

對策略模板、實例、用戶認證與訂閱進行全量管理。透過 cron 掃描 RUNNING 實例，**僅在該實例最新已完成的 4h 聚合桶尚未處理時**執行一次 `Step()`。透過 WebSocket Hub 下發交易指令給連接中的 LocalAgent，並接收成交上報。

**不執行：** GA 進化與回測運算（透過 `app_role` 在路由層攔截寫接口）。
**不保存：** 任何交易所 API 憑證。

### 2.2 LocalAgent 執行端（用戶本地）

極簡二進制進程，用戶本地執行。配置檔（`config.agent.yaml`）內保存 SaaS 連線資訊與 **Binance** API 憑證。

職責：
1. 啟動時透過 SaaS REST 登入取得 JWT
2. 用 JWT 建立 WebSocket 長連線到 SaaS `/ws/agent`
3. 收到 `TradeCommand` 後呼叫 Binance Spot REST API 執行現貨下單
4. 取得成交明細與當前餘額，建構 `DeltaReport` 上報 SaaS
5. 定時發送心跳；斷線後以指數退避自動重連

**不含：** 任何策略代碼，不連線資料庫，不自主決策。

### 2.3 進化算力面（本地實驗室，`app_role: lab`）

也是完整 SaaS 系統，但部署在本地算力機器上。資料庫連線雲端 SaaS 的同一個 Postgres 實例，專注執行 GA 進化任務與回測運算。

**不執行：** 真實交易指令下發（`app_role: lab` 在路由層禁用實例啟停與交易下發）。

### 2.4 `app_role` 三態行為矩陣

| 角色 | 部署場景 | 開放能力 | 限制 |
|------|---------|---------|------|
| `saas` | 雲端 SaaS | 實例管理、交易指令下發、用戶營運 | 禁止進化/回測寫接口 |
| `lab` | 本地實驗室 | GA 進化、回測、基因庫管理 | 禁止交易指令下發、實例只讀 |
| `dev` | 開發測試 | 所有模組全開 | 無限制 |

## 3. 邏輯模組與責任邊界

### 3.1 Strategy 策略模組（產品中心）

管理策略模板（圖紙）。定義策略的參數結構、版本標識、交易對類型（現貨）。當前主線策略為 `lunar-spot-v1`，面向 Binance 現貨 BTCUSDT / ETHUSDT。

`Step()` 是策略決策的唯一外部入口，所有買賣意圖、倉位規模、風控判斷均在 `Step()` 內產生。回測路徑與實盤路徑共用同一套 `Step()` 實作，**不允許內部分叉**。

### 3.2 Live/Instance 交易執行模組（設備中心）

實例（Instance）的本質是：**策略模板 + 交易標的 + 資金配額 + 用戶授權**。實例的建立、啟動、停止、刪除，以及執行中的狀態由此模組管理。

**實例狀態枚舉（4 態）：**

| 狀態 | 語義 | 進入條件 | 離開條件 |
|------|------|---------|---------|
| `RUNNING` | 運行中（cron tick 正常推進） | 用戶 Start，且 champion 存在 | 用戶 Stop / 異常 / champion 消失 |
| `STOPPED` | 已暫停（cron tick 跳過） | 用戶 Stop | 用戶 Start |
| `BLOCKED` | 等待人工干預（無 champion 可用） | `loadChampion` 回 `ErrNoChampion`（見進化文件 §6.2.3） | Promote 完成、新 champion 寫入 → 自動轉 RUNNING |
| `ERROR` | 異常需介入（divergence、reconcile 失敗等） | divergence 告警、嚴重錯誤 | 人工 reconcile + reset |

`BLOCKED` 與 `ERROR` 的區分：
- `BLOCKED`：**正常等待**狀態，等待人工 promote。系統自動恢復，不需人工修數據
- `ERROR`：**異常**狀態，需人工 reconcile（如帳本不一致、API key 失效）

cron 按基礎掃描頻率檢查所有 `RUNNING` 與 `BLOCKED` 狀態實例：
- `RUNNING`：完整 tick 流程（loadChampion → Step() → 下單）
- `BLOCKED`：只跑「輕量 champion 探測」（`loadChampion` 嘗試），成功則轉 `RUNNING`、失敗維持 `BLOCKED`，**不**進 Step()
- `STOPPED` / `ERROR`：完全跳過

實例 tick 只有在最新已完成的 4h 聚合桶未處理過時才推進：拉取公開 K 線數據，讀取 `PortfolioState`，建構 `StrategyInput`，呼叫 `Step()`，將產出的交易意圖翻譯為 `TradeCommand`，透過 WebSocket Hub 下發給已連接的對應 Agent。

**BLOCKED 自動恢復路徑（兩條）：**
1. **被動：cron 探測** — 每分鐘 cron 掃描時對 BLOCKED 實例呼叫 `loadChampion`，成功則 transition 至 `RUNNING`（最壞延遲 < 1 分鐘）
2. **主動：promote wake-up** — `Promote` 事務 commit 後，立即 SELECT 該 (strategy_id, symbol) 下所有 `BLOCKED` 實例 → 標記為 `RUNNING`（最壞延遲 < 1 秒）

兩條路徑同時存在做為 belt-and-suspenders。被動探測是 fallback，避免 promote 時某個 BLOCKED 實例剛建立尚未進 DB query 範圍時被漏掉。

### 3.3 Evolution & Backtest 模組（參數實驗室）

透過 GA 遺傳演算法對策略參數進行進化迭代，產出 **挑戰者（challenger）** 參數包。人工在前端審批後可將挑戰者晉升為 **冠軍（champion）**。冠軍參數包用於實例建立或參數更新。

只在 `app_role: lab` 或 `dev` 下開放進化任務建立與執行，回測路徑呼叫與實盤相同的策略 `Step()` 實作。

### 3.4 User/Auth 模組

處理用戶註冊、登入、JWT 簽發，以及訂閱計畫校驗（建立實例、啟動實例時做配額守門）。此模組不涉及策略邏輯，不在本文件細化。

## 4. 全局狀態總線

### 4.1 單一 Postgres + 單一 Redis

整個系統使用**單一** Postgres 資料庫（`eighti_quant`），不再區分 Shell DB 與 Live DB。Redis 僅作快取使用（冠軍基因 key、Session、AI 訊號 TTL），**不**承擔信號傳遞職責。

### 4.2 資料真源與所有權

| 資料 | 真源 | 說明 |
|------|------|------|
| 策略決策邏輯 | `Step()` 實作（SaaS 側執行） | 回測與實盤必須共用 |
| 冠軍參數包 / 模板 | SaaS DB | 進化產出，供實例綁定 |
| 終端用戶與訂閱 | SaaS DB | 統一在 SaaS 管理 |
| 執行中實例狀態 | SaaS DB | 由 Agent 上報後維護 |
| Binance API 憑證 | LocalAgent 本地配置檔 | 僅 Agent 持有，永不進入 SaaS DB |
| 成交記錄與資產快照 | SaaS DB | Agent 上報後持久化 |
| GA 任務與基因紀錄 | SaaS DB | 單一資料庫，無分庫 |

### 4.3 交易所憑證物理隔離鐵律

Binance API Key / Secret **只能**存在於 LocalAgent 的本地配置檔（`config.agent.yaml`）中。

- 永不進入 SaaS 服務
- 永不寫入任何資料庫表
- 永不透過網路傳輸到雲端

發現代碼將 API Key 寫入 SaaS 側時，**必須立即停止並報告**。

## 5. IoT 下發與上報通訊協議

雲端與端側嚴格遵循「**雲端只信上報，端側無腦執行**」機制，徹底解決網路斷線、丟包與髒資料問題。

### 5.1 WebSocket 長連線模型

Agent 發起連線，SaaS 監聽 `/ws/agent` 端點。連線建立時 Agent 必須先發送含 JWT 的鑑權訊息，SaaS 驗證通過後返回鑑權結果，之後進入正常收發循環。Agent 每 30 秒發送一次心跳，SaaS 回確認。

### 5.2 訊息類型全表

| 訊息類型 | 方向 | 觸發時機 |
|---------|------|---------|
| `auth` | Agent → SaaS | 連線建立後立即發送，攜帶 JWT |
| `auth_result` | SaaS → Agent | 鑑權完成後返回 |
| `heartbeat` | Agent → SaaS | 每 30 秒 |
| `heartbeat_ack` | SaaS → Agent | 收到心跳後 |
| `command` | SaaS → Agent | `Step()` 產出意圖後，SaaS 翻譯為具體指令下發 |
| `command_ack` | Agent → SaaS | 收到 command 後立即確認（不等執行完成） |
| `delta_report` | Agent → SaaS | 交易執行完成後；或重連時的初始餘額快照 |
| `report_ack` | SaaS → Agent | SaaS 成功處理 DeltaReport 後 |

### 5.3 TradeCommand 語義

每條 `TradeCommand` 攜帶以下語義欄位：

| 欄位 | 取值範圍 | 說明 |
|------|---------|------|
| `client_order_id` | 全局唯一字串 | 格式：`inst{id}-{engine}-{action}-{barTimeMs}-{seq}`，用於去重與審計 |
| `action` | `BUY` / `SELL`（大寫） | 交易方向 |
| `engine` | `MACRO` / `MICRO`（大寫） | 產生此指令的引擎層 |
| `symbol` | `BTCUSDT` / `ETHUSDT` | 交易對 |
| `amount_usdt` | 字串金額 | 買入時使用，表示花費 USDT 數量 |
| `qty_asset` | 字串數量 | 賣出時使用，表示賣出標的資產數量 |
| `lot_type` | `DEAD` / `FLOAT` | 倉位語義，宏觀吸入底倉 vs 微觀浮動倉 |

SaaS 下發 TradeCommand 的同時在資料庫寫一條 pending 紀錄，供 DeltaReport 回填時按 `LotType` 拆分更新 `DeadAsset` / `FloatAsset`。

**`client_order_id` 格式詳解：**
- `inst{id}` — 實例 ID
- `{engine}` — `M`（MACRO）或 `m`（MICRO），單字元節省字節
- `{action}` — `B`（BUY）或 `S`（SELL）
- `{barTimeMs}` — 本次 tick 對應的 `LatestBarTimeMs`
- `{seq}` — 同 tick 內若產出多筆同 engine+action 指令，從 0 遞增

範例：`inst42-M-B-1714521600000-0` = 實例 42 的 4h bar 在 2024-05-01 00:00 UTC 觸發的 MACRO BUY 第一筆。Binance API 對 `newClientOrderId` 唯一性要求嚴格，加 seq 確保同 tick 不撞 ID。

### 5.4 DeltaReport 語義

Agent 執行完畢後上報，包含：
- `balances`：當前所有資產的餘額快照（標的資產與 USDT 的可用與凍結）
- `execution`：本次成交明細（成交量、成交價格、手續費、狀態）
- `client_order_id`：對應的指令 ID（重連時發送初始快照時可為空）

### 5.5 狀態收斂與天然自癒

SaaS 收到 DeltaReport 後刷新對應實例的 `PortfolioState`，持久化 `SpotExecution` 與 `TradeRecord`，並寫審計日誌。

下次 `Step()` 呼叫時，系統基於真實餘額與語義拆分重新決策。這意味著：
- Agent 斷線後 SaaS 跳過該實例的 tick，無須人工干預
- Agent 重連後立即發送初始餘額快照，SaaS 在下次 tick 自動矯正
- SaaS 重啟後從 DB 恢復 `RUNNING` 與 `BLOCKED` 實例列表（見 §6.1），等待 Agent 重連

#### 5.5.1 Agent 重連後的 4 種 Reconcile 場景

| 場景 | SaaS 收到的訊息序 | Reconcile 動作 |
|------|------------------|---------------|
| **A. 平靜斷線**（斷線中無 pending command） | 重連 + 初始快照 | 走 §5.5.4 帳本一致性檢查：若 `SUM(lots by type) == snapshot balances`（容差 ≤ LotMinQty）→ 通過，instance 維持 RUNNING；若不等 → instance 標記 `ERROR`，等待人工 reconcile，**禁止繼續交易** |
| **B. SaaS 已下 command、Agent 沒收到** | 重連 + 初始快照 | Agent 連線後 SaaS 觸發 `ReconcilePendings`：見 §5.5.1.1 演算法 |
| **C. Agent 已執行、沒回 delta_report** | 重連 + 初始快照（資產已動） | 同 B（§5.5.1.1）；該情境下 `GET /api/v3/order` 必回 status=FILLED |
| **D. 重連快照 + delta_report 順序錯亂** | 先收到 delta_report、後收到快照 | 以 `delta_report.client_order_id` 為主鍵正常處理 delta_report；隨後收到快照時做「等價性驗證」（快照的 USDT/Asset 應等於帳本算出的 expected balance），不等則標記 `divergence`，告警 |

**核心原則：**
1. **client_order_id 是真源**：所有 SpotExecution 以 client_order_id 配對，配對失敗才走補救路徑
2. **快照只用於餘額覆寫**：不單獨用快照產生新的 lot 紀錄（lot 必須有 client_order_id 來源）
3. **pending 終態必須由交易所證據決定**：禁止「超過 N 分鐘自動 expired」，慢成交/Agent 上報延遲不該被誤判為「未執行」，否則下次 tick 會重複下單造成雙倍曝險
4. **divergence 告警必須 block 後續 trade**：實例狀態改為 `ERROR`，等待人工 reconcile

#### 5.5.1.1 ReconcilePendings 演算法（Binance Spot REST v3）

對每筆 `pending SpotExecution`（依 client_order_id），透過 Agent 呼叫 Binance API 推導終態：

```
ReconcilePending(pending) -> Action {
    // Step 1: 查詢該訂單在 Binance 側的當前狀態
    resp, err := agent.BinanceGetOrder(symbol=pending.Symbol, origClientOrderId=pending.ClientOrderID)

    // Binance error -2013 = "Order does not exist"
    // 通常代表訂單從未被交易所接受（網路丟包 / Agent 崩潰時還沒送出）
    if err.Code == -2013:
        return Action.MarkCanceled

    if err != nil:
        // 其他錯誤（網路 / 速率限制）→ 維持 pending，下次 tick 再試
        return Action.KeepPending

    // Step 2: 依 status 處置
    switch resp.Status:
        case "NEW", "PARTIALLY_FILLED":
            // 訂單仍 open
            // PARTIALLY_FILLED 也視為仍 open（後續會繼續成交直到 FILLED 或 CANCELED）
            return Action.KeepPending

        case "FILLED":
            // 完全成交，補建 SpotExecution
            fills := agent.BinanceGetMyTrades(symbol=pending.Symbol, orderId=resp.OrderId)
            return Action.MarkFilled(fills)

        case "CANCELED", "EXPIRED", "REJECTED", "EXPIRED_IN_MATCH":
            // 終態：未成交
            // PARTIALLY_FILLED 之後被 cancel 的特殊情境：用 fills 判斷有無部分成交
            if resp.ExecutedQty > 0:
                // 有部分成交 → 仍要補建 SpotExecution（執行量為 ExecutedQty）
                fills := agent.BinanceGetMyTrades(symbol=pending.Symbol, orderId=resp.OrderId)
                return Action.MarkPartiallyFilledThenCanceled(fills)
            else:
                return Action.MarkCanceled

        case "PENDING_CANCEL":
            // 內部過渡狀態，少見；維持 pending 等下次查
            return Action.KeepPending

        default:
            // 未知 status，告警 + 維持 pending（保守）
            log.Warn("unknown order status", resp.Status)
            return Action.KeepPending
}
```

**關鍵點：**
1. **Binance `GET /api/v3/openOrders` 不接受 `origClientOrderId` 參數**，且只能查當前 open 訂單。本演算法**不用** `openOrders`，改用 `GET /api/v3/order` 查任何訂單（含已 close 的）
2. **`/api/v3/order` 的 status 欄位是真源**，包含完整生命週期（`NEW` → `PARTIALLY_FILLED` → `FILLED` 或 `CANCELED` 或 `EXPIRED`）
3. **`PARTIALLY_FILLED` 仍視為 pending**，因為後續會繼續成交。但若 status 變成 `CANCELED` 且 `ExecutedQty > 0`，要把已成交的部分補建 SpotExecution
4. **myTrades 用 orderId 查**，不是 clientOrderId（因為 Binance trades API 只支援 orderId）

**Action 類型對應 SaaS 端動作：**
- `KeepPending` — 不動
- `MarkFilled(fills)` — UPDATE pending → status=`filled`，建 SpotExecution + 更新 PortfolioState；**無需 runtime 補償**
- `MarkPartiallyFilledThenCanceled(fills)` — 部分成交，按實際 ExecutedQty 建 SpotExecution；**runtime 補償未成交部分**（見下方）
- `MarkCanceled` — UPDATE pending → status=`canceled`，不建 SpotExecution；**runtime 補償全額**（見下方）

#### 5.5.1.2 Cancellation Compensation（runtime + lot rollback）

當 pending 終態為 `canceled` 或部分成交（即「**意圖未完整實現**」），SaaS 必須執行補償：

**A. Macro BUY 取消時的 runtime 補償**

若被 cancel 的 pending 是 `engine=MACRO, action=BUY`：

```
unfilledAmount = pending.OrigAmountUSDT - executedAmountUSDT  // canceled = OrigAmount，partial = OrigAmount - ExecutedAmount

# 反向 mutation（補回 Step() 當初 emit intent 時的扣帳）
RuntimeState.Macro.SpentThisMonth     -= unfilledAmount
RuntimeState.Macro.PendingMacroBudget += unfilledAmount

# LastMacroBuyBarTime 不 reverse — 同 bar 不重買原則保留（避免無限重試）
# 實際效果：該 bar 的預算累積會延到下次 4h tick 才能消化
```

寫 audit log `event_type=macro_runtime_compensated`，含 unfilledAmount 與 client_order_id。

**B. Micro 取消時的 runtime 補償**

Micro 引擎不維護累積式 runtime（每 tick 從 Sigmoid 重新計算），**無需補償**。但對應的 `ReleaseIntent` 需處理（見 C）。

**C. Hard Release 對應 SELL 取消時的 lot rollback**

若被 cancel 的 pending 是 `lot_type=FLOAT, action=SELL`，且該 client_order_id 在 audit log 中對應一個 `event_type=hard_release` 條目（透過 `ReleaseIntent.RelatedClientOrderID` 配對）：

```
# 找出該 hard_release 觸發轉換的 lots
related_release = audit_logs.find(event_type='hard_release',
                                  related_client_order_id=pending.ClientOrderID)

# Rollback 每個 ReleaseSlice：把 FLOAT lot 改回 DEAD
for slice in related_release.Slices:
    UPDATE spot_lots
       SET type = 'DEAD'
     WHERE id = slice.LotID
       # 注意：BuyPriceUSDT 與 BuyTimeMs 在 release 時已保留，此處不變
```

寫 audit log `event_type=hard_release_rolled_back`。

**D. Soft Release 不需 rollback**

`soft_release` 是純應用層 lot type 標籤轉換（DEAD 老化釋放），**不對應任何 SELL 訂單**。`RelatedClientOrderID` 為空，cancellation 不會觸發 rollback。

**E. Partial fill 的處理**

`MarkPartiallyFilledThenCanceled`：
- BUY partial-fill：成交部分照常進帳本（建 SpotExecution）；未成交部分走 A 的補償
- SELL partial-fill：成交部分減少 FLOAT；未成交部分對應的 hard_release lot rollback（slice 中 partial qty 處理見實作細則）

**F. 補償操作的原子性**

A/B/C 的補償**必須與 pending 狀態變更同 transaction**：

```
BEGIN TX:
  UPDATE pending SET status = 'canceled' WHERE id = ?
  UPDATE strategy_instances SET runtime_state = jsonb_set(...) WHERE id = ?  -- A
  UPDATE spot_lots SET type = 'DEAD' WHERE id IN (...)                       -- C
  INSERT INTO audit_logs (...) VALUES (...)
COMMIT
```

避免「pending 已 canceled 但 runtime 沒補償」造成永久不一致。

#### 5.5.2 Tick 前的 Pending 預檢

每個 cron tick **在呼叫 `Step()` 之前**，必須檢查實例是否有 `pending SpotExecution`：

```
1. SELECT * FROM spot_executions WHERE instance_id = ? AND status = 'pending'
2. 若 pending 非空：
     a. Agent 在線 → 觸發 ReconcilePendings（同 §5.5.1 場景 B/C 的查詢路徑）
        若仍有 pending（交易所回 still open）→ 跳過此 tick
     b. Agent 離線 → 跳過此 tick（不下新單）
3. pending 全部已轉終態（filled/canceled）→ 正常進 Step()
```

**設計理由**：實盤交易最不可逆的錯誤是「同一決策意圖下成兩次單」。任何 pending 在「下一個 tick 開頭」都必須被解決或暫緩，否則該 tick 跳過。寧可慢一個 4h tick，不可重複下單。

#### 5.5.3 SaaS 重啟恢復

SaaS 重啟時：
1. Load 所有 `RUNNING` **與 `BLOCKED`** 實例（不論 pending 狀態）；`STOPPED` / `ERROR` 不載入
2. Load 所有 `pending SpotExecution`（**沒有時間上限**）
3. 等待對應 Agent 重連 → 觸發 §5.5.1 的 reconcile 流程
4. Agent 重連前 cron tick 跳過該實例（同 §5.5.2 規則 b）

**取消「30 分鐘自動 expired」**。pending 永遠等到交易所給出明確證據（成交或不存在）才能轉終態。極端情境（Agent 永久離線 + 交易所無記錄）視為運維異常，需人工介入，不會自動 expire 後重複下單。

#### 5.5.4 帳本一致性檢查（Lot vs Balance Reconciliation）

每次 Agent 重連送入 `初始快照` 後，SaaS 必須驗證**lot 帳本總和**與**snapshot 餘額**一致：

```
expectedDeadAsset       = SUM(lot.Qty for lot in Lots if lot.Type == "DEAD")
expectedFloatAsset      = SUM(lot.Qty for lot in Lots if lot.Type == "FLOAT")
expectedColdSealedAsset = SUM(lot.Qty for lot in Lots if lot.Type == "COLD_SEALED")
expectedTotalAsset      = expectedDeadAsset + expectedFloatAsset + expectedColdSealedAsset

if abs(expectedTotalAsset - snapshot.assetBalance) > LotMinQty:
    instance.state = ERROR
    audit.Log("balance_lot_divergence", {
        expected: expectedTotalAsset,
        snapshot: snapshot.assetBalance,
        diff: snapshot.assetBalance - expectedTotalAsset,
    })
    alert(operator)
    return  // 禁止繼續交易
```

**為什麼這個檢查不可或缺：**

審查發現原版 §A 場景描述「用快照覆寫 balances，保留 lots」會造成 `SUM(lots) != balances` 的隱性帳本破壞。後續 release/sell 邏輯：
- `release.MaybeSoftRelease` 用 lots 決定可釋放量
- `Step()` 用 `Portfolio.DeadAsset/FloatAsset` 算 `TotalEquity` 跟 `CurrentMicroWeight`
- 兩者基於不同數字 → 「想釋放 X，但帳上 balance 跟得上 lots 嗎？」答案不對 → 漏單 / 重複下單 / 帳本崩潰

斷線中可能造成 lot vs balance 不一致的事件：
- 用戶手動在 Binance 介面操作（買、賣、轉帳）
- 部分成交手續費沒進 audit log
- Agent 故障期間有未上報的 fill
- 歷史帳本本身已有 drift（過去某次 reconcile 沒修乾淨）

**恢復路徑：**

`ERROR` 狀態進入 lot ledger 重建流程（手動）：
1. 運維拿 SaaS 帳本 + Binance 歷史成交（`GET /api/v3/myTrades` 跨完整時間範圍）對帳
2. 修復 SpotLot 或 PortfolioState 至一致
3. 通過驗證後人工 reset state 至 RUNNING

**容差說明：**

`LotMinQty`（BTC: 0.00001, ETH: 0.0001）作為容差是因為交易所 fill 的捨入誤差可能累積到此量級。容差再大就會掩蓋真實 drift；再小會誤觸發。此值由 SpawnPoint.RiskBounds 提供。

## 6. 系統級生命週期動作

### 6.1 系統初始化（System Init）

**觸發時機：** SaaS 進程啟動時。

**動作流轉：**
1. 讀取配置檔（`config.yaml`），初始化 DB 連線、Redis 連線、JWT 秘鑰
2. 執行 GORM AutoMigrate，以 Go struct 為唯一 schema 真源完成資料庫結構同步
3. 從 DB 讀取所有狀態為 `RUNNING` 與 `BLOCKED` 的實例，註冊到記憶體管理列表（BLOCKED 實例由 cron 輕量探測恢復，見 §3.2）
4. 啟動 WebSocket Hub，開始接受 Agent 連線
5. 啟動 cron 調度器，註冊實例基礎掃描任務；具體 `Step()` 推進由每個實例的聚合桶去重控制

### 6.2 Cron Tick 驅動實例 Step()

**觸發時機：** cron 基礎掃描命中 `RUNNING` 實例後，若該實例最新已完成的聚合桶尚未處理，則觸發一次 `Step()`；已處理過同一桶時跳過，避免實盤比回測多跑決策。

**動作流轉（前置安全閘 + Step() + 派單，按順序執行）：**

```
# ──────────── Phase A: 前置安全閘（任一失敗即跳過 tick） ────────────
1. 載入 champion（loadChampion，version-aware read-through）
   - ErrNoChampion → 標記 instance state = BLOCKED + audit log → return
     （見 進化計算引擎.md §6.2.2 / §6.2.3）
   - 其他 error → log + return（下次 tick 再試）

2. 同 bar 去重檢查
   - 取得最新已完成 4h bar 的 LatestBarTimeMs
   - 若 LatestBarTimeMs <= PortfolioState.LastProcessedBarTime → return（已處理）

3. Pending 預檢（見 §5.5.2）
   - SELECT pending SpotExecution where instance_id = ?
   - 若有 pending：
     * Agent 在線 → 觸發 ReconcilePendings（§5.5.1.1）
       仍 pending 未完成 → return
     * Agent 離線 → return（不下新單）

4. Lot vs Balance 一致性檢查（見 §5.5.4）
   - 若 SUM(lots by type) != PortfolioState 餘額（容差 LotMinQty）
     → 標 instance state = ERROR + alert → return

# ──────────── Phase B: Step() 執行 ────────────
5. 從 Binance 公開 API 拉取 K 線歷史數據（≥ 600 根 4h bar）
6. 從 DB 讀取 PortfolioState（含 Lots）+ RuntimeState
7. 建構 StrategyInput（K 線、Portfolio、RuntimeState、時間戳，
   時間戳一律用 LatestBarTimeMs，不用 NowMs）
8. 呼叫 panel.Step()（**只在 SaaS 側執行**，Agent 不含此邏輯）

# ──────────── Phase C: 原子持久化 + 派單 ────────────
# 關鍵：步驟 9-13 必須在同一個 DB transaction 內 commit
# 否則 Step() 已 mutate runtime（PendingMacroBudget / SpentThisMonth /
# LastMacroBuyBarTime）但 pending 沒寫成功 → 下次 tick 看到 mutated runtime
# 但無對應 pending order → 訂單永遠丟失
BEGIN TX:
  9.  將 Intents 翻譯為 TradeCommand（含 client_order_id = inst{id}-{engine}-{action}-{barTimeMs}-{seq}）
  10. 在 DB 寫入 pending SpotExecution 紀錄（每筆 Intent 一筆）
  11. 持久化 Step() 產出的 NewRuntime 到 DB
  12. 處理 Releases（DEAD↔FLOAT 帳本轉換，更新 SpotLot 表，**不**下發 Agent）
  13. 寫 audit log（trade_intent / release / step_diagnostics）
  14. 更新 PortfolioState.LastProcessedBarTime = LatestBarTimeMs
COMMIT TX

# Phase D: WS dispatch（在 commit 之後，不阻塞 TX）
15. 透過 WebSocket Hub 將 TradeCommand 下發給對應 Agent
    - dispatch 失敗（Agent 離線、WS 錯誤）不重試此 tick
    - 下次 tick 走 §5.5.2 ReconcilePendings 路徑補救（pending 已在 DB，不會丟）
```

**關鍵不變式：**
- Phase A 任一閘失敗 → 直接 return，**不**進 Phase B/C/D
- Phase B 開始前，instance 已有合法 champion + 帳本一致 + 無未完成 pending
- **Phase C 步驟 9-14 必須原子 commit**（同一 DB TX）：runtime mutation、pending 寫入、bar 處理標記三者**同生同死**
- Phase C TX 失敗 → 整批回滾 → 下次 tick 重跑（不會看到 partial state，idempotent guard 不會誤判）
- Phase D WS dispatch 失敗 → DB 仍有 pending → 走 ReconcilePendings 補救

**為什麼必須原子化：**

審查發現原版「先 persist runtime → 再 write pending」順序在中間失敗時會：
1. runtime 已 mutate（`PendingMacroBudget` 已減去、`SpentThisMonth` 已加上、`LastMacroBuyBarTime` 已更新）
2. pending 沒寫進 DB
3. 下次 tick 觸發 §0.1.1 idempotent guard `LastMacroBuyBarTime == LatestBarTimeMs`，return 0
4. **訂單永遠不會下**，但月度預算已經被「花掉」（從 `SpentThisMonth` 看是花了，實際上沒下單）

原子化後三者同生同死，partial failure 直接 rollback，下次 tick 完整重跑。

### 6.3 Agent 斷線重連

**觸發時機：** Agent 偵測到 WebSocket 連線斷開。

**動作流轉：**
1. 等待初始退避時間（1 秒），嘗試重新登入取得 JWT
2. 建立新的 WebSocket 連線
3. 連線建立後立即發送初始 `DeltaReport`（當前 Binance 餘額快照，不含 `client_order_id` 與 `execution`）
4. SaaS 收到快照後更新相關實例的 `PortfolioState`
5. 下次 cron tick 時，SaaS 基於真實餘額重新決策，無需人工干預

重連退避策略：初始 1 秒，每次翻倍，最大等待 5 分鐘。

### 6.4 優雅停機與狀態快照（Graceful Shutdown）

**觸發時機：** SaaS 進程接收到作業系統中斷訊號（如 `SIGTERM`）。

**動作流轉：**
1. 停止接受新的 Agent 連線與 cron tick 任務
2. 等待正在執行中的 tick 完成（超時保護 30s）
3. 持久化所有活躍實例的 `RuntimeState` 快照，避免重啟後策略狀態撕裂
4. 關閉所有 WebSocket 連線，發送關閉幀
5. 關閉 DB 與 Redis 連線

## 7. 不可推翻的技術決策

以下為整個系統的硬約束，違反時必須停止開發並報告，不得繞過。

**1. 複利前置條件（鐵律）**
任何涉及策略機制的設計或實作，必須能清楚說明複利如何發生（資金規模隨權益正反饋滾動）。不滿足可論證複利性質的策略設計，不進行開發。

**2. 策略同構原則**
回測與實盤必須呼叫同一個 `Step()` 實作。`Step()` 內部禁止出現 `if isBacktest { ... } else { ... }` 類分支。`Step()` 只在 SaaS 側執行，Agent 二進制不包含任何策略代碼。

**3. 策略內部純淨原則**
策略代碼內部絕對禁止：計時器、網路請求（HTTP / WebSocket / gRPC）、資料庫讀寫、任何檔案 I/O。策略是純函數，只依賴傳入的 `StrategyInput`，只輸出 `StrategyOutput`。

**4. 現貨策略 ACL OHLC 剝離**
`Manifest.IsSpot == true` 的策略，內核代碼禁止依賴 `OHLCV` 聚合結構（`quant.Bar`）。所有 OHLCV 到 `[]float64 + []int64`（收盤價序列 + 時間戳序列）的降級必須在 ACL 外圈（回測適配器入口與實盤 tick 入口）完成。

**5. API Key 物理隔離**
Binance API Key / Secret 只允許存在於 LocalAgent 的本地配置檔中，永不進入 SaaS，永不寫入資料庫，永不透過網路傳輸。

**6. GORM AutoMigrate 為表結構真源；indexes.sql 為非結構性 DB 物件唯一管道**

資料庫**表結構**（tables / columns / types）以 Go struct 為真源，透過 GORM AutoMigrate 管理。不寫 SQL migration 檔案改變表結構，不維護版本化 migration 腳本，不手動 ALTER TABLE。

**例外（必要）：** GORM struct tag 表達不了的 DB 物件（PostgreSQL partial index、check constraint 等）必須寫進 `internal/saas/store/indexes.sql`，由 `db.go` 在 AutoMigrate 之後 `db.Exec(ddl)` 執行。當前已知用例：

- `uniq_active_champion` partial unique index（強制單一 champion 不變式，見 `進化計算引擎.md` §6.2.1.1）

完整規則見 `CLAUDE.md` §2.4。

**7. 無量綱計算**
所有價格相關計算使用對數收益率或比率（無量綱），禁止用絕對價格做跨標的比較。

**8. 倉位三態**
資產狀態以 `DeadAsset`（宏觀長期底倉）/ `FloatAsset`（微觀浮動倉）/ `ColdSealedAsset`（冷封存，永不釋放）三態區分語義，不能混用。倉位三態的更新規則由策略 `Step()` 決定，SaaS 按 `LotType` 欄位（`"DEAD"` / `"FLOAT"` / `"COLD_SEALED"`）落帳。命名 canonical table 見 `策略數學引擎.md` §1.1。

**9. 底倉釋放僅在 SaaS 側更新，不下發 Agent**
`DeadAsset → FloatAsset` 的語義轉換（即軟釋放/硬釋放，由 `策略數學引擎.md` §6 規範）只改變 SaaS 側的 `PortfolioState` 帳本（`SpotLot.LotType` 從 `"DEAD"` 改為 `"FLOAT"`），不向 Agent 下發任何 `TradeCommand`，但必須寫審計日誌。

**10. 單一資料庫，無分庫**
SaaS 使用單一 Postgres 實例，不分 Shell DB 與 Live DB，不使用 Redis 作為訊號傳遞通道（Redis 僅作快取）。

**11. 用戶界面零數學**
面向用戶的字串中避免出現內部狀態機術語、無上下文的裸數學量名或公式片段。希臘字母並非一律禁止；若含義上必須保留，應採用「字母 + 文字釋義」並置（例如「σ（標準差）」「ρ（相關係數）」），禁止僅展示希臘字母而無對應說明。
